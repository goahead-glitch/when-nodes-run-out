## 1. 포트 및 수집 엔드포인트 확정

> 코드 직접 확인 기준. 설계에서 가정한 값이 아니라 실제 동작하는 값.

### 서비스 포트

| 서비스 | 컨테이너 포트 | /metrics 위치 | 비고 |
|---|:---:|---|---|
| Frontend (Nginx) | **80** | 없음 | docker-compose `3000:80` — 호스트 3000이 컨테이너 80에 매핑 |
| API Gateway | **4000** | `4000/metrics` | 앱과 같은 포트 |
| Product Service | **4001** | `4001/metrics` | |
| Inventory Service | **4002** | `4002/metrics` | |
| Order Service | **4003** | `4003/metrics` | |
| Payment Service | **4004** | `4004/metrics` | |
| User Service | **4005** | `4005/metrics` | |

### 인프라 Exporter 포트

| Exporter | 배포 방식 | 실행 위치 | 포트 |
|---|---|---|:---:|
| **kube-state-metrics** | k8s **Deployment** (1개) | 워커노드 중 하나에 스케줄 → k8s API Server에 쿼리 | **8080** → NodePort |
| **node_exporter** | k8s **DaemonSet** (모든 노드에 1개씩) | 마스터 + 워커 전체 | **9100** (노드IP 직접) |
| postgresql_exporter | EC2 직접 설치 (온프레미스) | PostgreSQL EC2 | **9187** |
| postgresql_exporter | k8s **Pod** (EKS) | EKS RDS는 VPC 내부에서만 접근 → Pod로 배포 후 NodePort | NodePort |
| redis_exporter | EC2 직접 설치 | Redis EC2 (양쪽) | **9121** |

> **kube-state-metrics vs node_exporter 차이:**
> - kube-state-metrics: 클러스터 전체에 **1개**만 뜸. k8s API Server에 물어봐서 파드·노드·HPA 같은 **k8s 오브젝트 상태**를 수집
> - node_exporter: **모든 노드에 각 1개**씩 뜸. 해당 노드의 **OS 수준** (CPU, Memory, 디스크)을 수집

### k8s에서 Prometheus scrape 방식

```
Prometheus (VPC-A t3.small)
  │
  ├── 앱 서비스 메트릭 (prom-client, /metrics)
  │     온프레미스: c8i.2xlarge 사설IP : NodePort
  │     EKS:       Worker Node 공인IP  : NodePort
  │
  ├── kube-state-metrics (Deployment Pod 1개)
  │     온프레미스: c8i.2xlarge 사설IP : NodePort  ← Pod가 어느 워커에 있든 NodePort로 접근
  │     EKS:       Worker Node 공인IP  : NodePort
  │
  ├── node_exporter (DaemonSet — 노드마다 1개)
  │     온프레미스: VM2 <worker1-VM-IP>:9100  ← 워커노드 1
  │                VM3 <worker2-VM-IP>:9100  ← 워커노드 2
  │                VM1 <master-VM-IP>:9100  ← 마스터 (참고용)
  │     EKS:       Worker Node1 공인IP:9100
  │                Worker Node2 공인IP:9100
  │
  ├── PostgreSQL Exporter
  │     온프레미스: PostgreSQL EC2 사설IP:9187
  │     EKS:       k8s Pod → Worker Node 공인IP:NodePort
  │
  └── Redis Exporter
        온프레미스: Redis EC2 사설IP:9121
        EKS:       Redis EC2 공인IP:9121
```

## 3. 왜 이걸 수집하는가 — 수집 목적별 분류

### 목적 A: 비교 결과 증명 — 발표에서 보여줄 것

이 지표들이 없으면 실험 자체가 성립하지 않는다.

| 지표 | 수집 도구 | 왜 필요한가 |
|---|---|---|
| **Pending Pod 수** | kube-state-metrics | "온프레미스는 자원 부족으로 파드가 쌓인다" — 발표 핵심 한 방 |
| **Node Count** | kube-state-metrics | "EKS는 Karpenter가 자동으로 노드를 추가한다" — 자동화 증거 |
| **HPA desired vs current** | kube-state-metrics | "늘리고 싶은데 못 늘린다" — 자원 부족 상태 정량화 |
| **Error Rate (5xx)** | prom-client (Gateway) | "온프레미스 37%, EKS 0.3%" — 비즈니스 임팩트 |
| **MTTR** | Error Rate 그래프 + 타임스탬프 | "복구 10분 vs 45초" — 시나리오 3 핵심 |

### 목적 B: 원인 설명 — 왜 저런 결과가 나왔는지

"데이터가 말한다"는 발표 메시지를 뒷받침하는 근거.

| 지표 | 수집 도구 | 왜 필요한가 |
|---|---|---|
| **CPU 사용률 per node** | node_exporter | "워커노드 1이 CPU 100%에 도달했기 때문에 Pending 발생" |
| **DB Active Connection** | postgresql_exporter | "커넥션이 고갈되어 쿼리가 대기 중" |
| **DB Lock 대기** | postgresql_exporter | "SELECT FOR UPDATE 충돌로 재고 처리가 지연" |
| **TPS** | prom-client (Gateway) | "온프레미스는 처리량이 한계에서 꺾임" |
| **P95 Latency** | prom-client (Gateway) | "응답시간이 얼마나 튀는지 — 사용자 체감 지표" |
| **재고 충돌 횟수** | prom-client (Inventory) | "동시 주문이 몰릴 때 충돌 건수 직접 측정" |
| **결제 성공/실패 수** | prom-client (Payment) | "장애 중 실제로 몇 건 손실됐는지" |
| **에러 로그 원인** *(선택)* | OpenSearch (Fluent Bit) | "왜 에러가 났는지" — DB 커넥션 고갈, timeout, OOM 등 실제 에러 메시지 |
| **MTTR 정밀 측정** *(선택)* | OpenSearch (Fluent Bit) | 로그 타임스탬프로 "마지막 성공 → 첫 복구" 초 단위 측정 |

### 목적 C: 실험 공정성 검증 — 조건이 동일했음을 증명

"같은 조건에서 비교했다"는 전제를 데이터로 증명.

| 지표 | 수집 도구 | 왜 필요한가 |
|---|---|---|
| **Redis 캐시 히트율** | redis_exporter | "양쪽 캐시 조건이 동일했음을 확인" |
| **Memory 사용률** | node_exporter | "노드 스펙이 동일했음을 확인" |

### 수집하지 않는 것 (이유 포함)

| 항목 | 제외 이유 |
|---|---|
| Frontend 메트릭 | 비교 대상 아님. 정적 파일 서빙은 두 환경에서 동일 |
| ALB 상세 메트릭 | Gateway prom-client Error Rate로 충분히 커버 |
| 서비스별 개별 TPS/Error Rate | Gateway가 전체를 대표. 엔드포인트별 응답시간으로 보완 |
| 디스크 I/O | 이 실험의 비교 변수가 아님 |

## 4. 실제 메트릭 이름 목록

> 코드에서 직접 확인한 값. PromQL 작성 시 이 이름을 사용해야 한다.

### prom-client — 각 서비스별 Histogram

모든 서비스는 Histogram 타입으로 HTTP 응답시간을 수집한다.  
Histogram에서 파생되는 suffix:
- `_bucket` → `histogram_quantile()`로 P95 계산
- `_count` → `rate()`로 TPS 계산
- `_sum` → 평균 응답시간 계산 (sum/count)

| 서비스 | 메트릭 이름 | 레이블 |
|---|---|---|
| API Gateway | `gateway_http_duration_seconds` | `method`, `route`, `status` |
| Product | `product_service_http_duration_seconds` | `method`, `route`, `status` |
| Inventory | `inventory_service_http_duration_seconds` | `method`, `route`, `status` |
| Inventory | `inventory_stock_conflicts_total` | (충돌 횟수 Counter) |
| Order | `order_service_http_duration_seconds` | `method`, `route`, `status` |
| Payment | `payment_service_http_duration_seconds` | `method`, `route`, `status` |
| Payment | `payment_processed_total` | (결제 처리 Counter) |
| User | `user_service_http_duration_seconds` | `method`, `route`, `status` |

### 환경 구분 레이블

Prometheus scrape 시 relabeling으로 `env` 레이블 자동 부여:
- 온프레미스에서 수집된 모든 메트릭: `env="onprem"`
- EKS에서 수집된 모든 메트릭: `env="eks"`

## 5. Prometheus scrape 설정

```yaml
# /etc/prometheus/prometheus.yml

global:
  scrape_interval: 15s
  scrape_timeout: 10s

scrape_configs:

  # ── 온프레미스 앱 메트릭 (Gateway가 핵심) ────────────────────
  - job_name: 'app-onprem'
    static_configs:
    - targets:
      - '<c8i.2xlarge-사설IP>:<gateway-NodePort>'     # Gateway :4000/metrics
      - '<c8i.2xlarge-사설IP>:<product-NodePort>'     # Product :4001/metrics
      - '<c8i.2xlarge-사설IP>:<inventory-NodePort>'   # Inventory :4002/metrics
      - '<c8i.2xlarge-사설IP>:<order-NodePort>'       # Order :4003/metrics
      - '<c8i.2xlarge-사설IP>:<payment-NodePort>'     # Payment :4004/metrics
    relabel_configs:
    - target_label: env
      replacement: onprem

  # ── EKS 앱 메트릭 ────────────────────────────────────────────
  - job_name: 'app-eks'
    static_configs:
    - targets:
      - '<EKS-worker1-공인IP>:<gateway-NodePort>'
      - '<EKS-worker1-공인IP>:<product-NodePort>'
      - '<EKS-worker1-공인IP>:<inventory-NodePort>'
      - '<EKS-worker2-공인IP>:<order-NodePort>'
      - '<EKS-worker2-공인IP>:<payment-NodePort>'
    relabel_configs:
    - target_label: env
      replacement: eks

  # ── 온프레미스 k8s 상태 ───────────────────────────────────────
  - job_name: 'kube-state-onprem'
    static_configs:
    - targets: ['<c8i.2xlarge-사설IP>:<kube-state-NodePort>']
    relabel_configs:
    - target_label: env
      replacement: onprem

  # ── EKS k8s 상태 ─────────────────────────────────────────────
  - job_name: 'kube-state-eks'
    static_configs:
    - targets: ['<EKS-worker-공인IP>:<kube-state-NodePort>']
    relabel_configs:
    - target_label: env
      replacement: eks

  # ── PostgreSQL Exporter (온프레미스) ─────────────────────────
  - job_name: 'postgres-onprem'
    static_configs:
    - targets: ['<PostgreSQL-EC2-사설IP>:9187']
    relabel_configs:
    - target_label: env
      replacement: onprem

  # ── PostgreSQL Exporter (EKS — k8s Pod NodePort) ─────────────
  - job_name: 'postgres-eks'
    static_configs:
    - targets: ['<EKS-worker-공인IP>:<pg-exporter-NodePort>']
    relabel_configs:
    - target_label: env
      replacement: eks

  # ── Redis Exporter ────────────────────────────────────────────
  - job_name: 'redis-onprem'
    static_configs:
    - targets: ['<Redis-EC2-사설IP>:9121']
    relabel_configs:
    - target_label: env
      replacement: onprem

  - job_name: 'redis-eks'
    static_configs:
    - targets: ['<EKS-Redis-공인IP>:9121']
    relabel_configs:
    - target_label: env
      replacement: eks

  # ── Node Exporter (온프레미스 VM 3대) ────────────────────────
  - job_name: 'node-onprem'
    static_configs:
    - targets:
      - '<master-VM-IP>:9100'   # VM1 마스터 (참고용)
      - '<worker1-VM-IP>:9100'   # VM2 워커노드 1 (traffic-node)
      - '<worker2-VM-IP>:9100'   # VM3 워커노드 2 (order-node)
    relabel_configs:
    - target_label: env
      replacement: onprem

  # ── Node Exporter (EKS 워커노드) ─────────────────────────────
  - job_name: 'node-eks'
    static_configs:
    - targets:
      - '<EKS-worker1-공인IP>:9100'
      - '<EKS-worker2-공인IP>:9100'
    relabel_configs:
    - target_label: env
      replacement: eks
```

## 6. Grafana 템플릿 패널

> Grafana 공식 템플릿에서 Import 후 필요한 패널만 최종 대시보드로 복사.

### 6-1. Node Exporter Full — ID: `1860`

가져올 패널:

| 패널명 | 목적 |
|---|---|
| CPU 사용률 | "워커노드 1 CPU 100% 도달 → Pending 발생" 증거 |
| Memory 사용률 | 양쪽 노드 스펙 동일했음 확인 (공정성 검증) |
| Network I/O | 네트워크 포화 여부 참고 |

설정: `job="node-onprem"` / `job="node-eks"` 변수 전환

### 6-2. Kubernetes Cluster Monitoring — ID: `315`

가져올 패널:

| 패널명 | 목적 |
|---|---|
| Pod Count | HPA 발동으로 파드가 늘어나는 흐름 |
| Node Count | EKS Karpenter 자동 노드 추가 순간 포착 |
| **Pending Pod** | **발표 임팩트 최강** — 온프레미스 쌓임 / EKS 0 유지 |

설정: `job="kube-state-onprem"` / `job="kube-state-eks"` 변수 전환

### 6-3. PostgreSQL Database — ID: `9628`

가져올 패널:

| 패널명 | 목적 |
|---|---|
| Active Connection | "커넥션 고갈 → 쿼리 대기" 원인 설명 |
| 쿼리 응답시간 | 느려지는 구간 특정 |
| Lock 대기 | `SELECT FOR UPDATE` / 낙관적 락 충돌 시각화 |

설정: `job="postgres-onprem"` / `job="postgres-eks"`, `datname="shoply"`

### 6-4. Redis Dashboard — ID: `11835`

가져올 패널:

| 패널명 | 목적 |
|---|---|
| 캐시 히트율 | 양쪽 캐시 조건 동일했음 확인 (공정성 검증) |
| Memory 사용량 | Redis 메모리 포화 여부 |

## 7. 직접 제작 패널 — PromQL 포함

> 양쪽 환경을 나란히 비교하거나 템플릿에 없는 것들은 직접 만든다.  
> 모든 PromQL은 코드에서 확인한 실제 메트릭 이름 기준.

---

### #1 TPS (초당 처리 요청 수)

**왜:** 트래픽 폭증 시 온프레미스 처리량이 한계에서 꺾이는 순간을 포착

Histogram의 `_count`를 `rate()`로 계산:

```promql
# 온프레미스
rate(gateway_http_duration_seconds_count{env="onprem"}[1m])

# EKS
rate(gateway_http_duration_seconds_count{env="eks"}[1m])
```

---

### #2 P95 Latency (95번째 백분위 응답시간)

**왜:** 폭증 시 응답시간이 얼마나 튀는지 — 사용자 체감 지표

```promql
# 온프레미스
histogram_quantile(0.95,
  rate(gateway_http_duration_seconds_bucket{env="onprem"}[1m])
)

# EKS
histogram_quantile(0.95,
  rate(gateway_http_duration_seconds_bucket{env="eks"}[1m])
)
```

---

### #3 Error Rate (5xx 비율)

**왜:** "온프레미스 37% vs EKS 0.3%" — 발표 임팩트 최강, 비즈니스 손실 직결

```promql
# 온프레미스
rate(gateway_http_duration_seconds_count{env="onprem", status=~"5.."}[1m])
/
rate(gateway_http_duration_seconds_count{env="onprem"}[1m])

# EKS
rate(gateway_http_duration_seconds_count{env="eks", status=~"5.."}[1m])
/
rate(gateway_http_duration_seconds_count{env="eks"}[1m])
```

단위: `percent (0.0~1.0)`, Grafana에서 `Unit → Percent (0.0-1.0)` 설정

---

### #4 Pod Count 타임라인

**왜:** HPA 발동으로 파드가 증가하는 흐름 확인

```promql
# 온프레미스 Running Pod 수
count(kube_pod_status_phase{phase="Running", env="onprem"})

# EKS Running Pod 수
count(kube_pod_status_phase{phase="Running", env="eks"})
```

---

### #5 Node Count 타임라인

**왜:** EKS Karpenter 자동 노드 추가 순간을 타임라인으로 포착

```promql
# 온프레미스 (2개 고정선)
count(kube_node_info{env="onprem"})

# EKS (트래픽 폭증 후 계단식 상승)
count(kube_node_info{env="eks"})
```

---

### #6 Pending Pod 타임라인 ★

**왜:** 이 패널 하나가 모든 것을 설명한다  
온프레미스 — 자원 부족으로 계속 쌓임 / EKS — Karpenter가 해소하여 0 유지

```promql
# 온프레미스 (쌓임)
count(kube_pod_status_phase{phase="Pending", env="onprem"})
or on() vector(0)

# EKS (0 유지)
count(kube_pod_status_phase{phase="Pending", env="eks"})
or on() vector(0)
```

> `or on() vector(0)`: `or vector(0)`는 Pending Pod가 0개일 때 레이블 없는 시리즈를 반환해 Grafana 범례가 깨질 수 있음.  
> `on()`으로 빈 매칭을 명시하면 0을 안전하게 반환하고 그래프가 끊기지 않음.

---

### #7 HPA desired vs current replicas

**왜:** "HPA는 5개 원하는데 2개밖에 없다" — 자원 부족 상태를 정량으로 보여줌

```promql
# 온프레미스 — desired (원하는 수)
kube_horizontalpodautoscaler_status_desired_replicas{env="onprem"}

# 온프레미스 — current (실제 수)
kube_horizontalpodautoscaler_status_current_replicas{env="onprem"}

# EKS도 동일 (env="eks")
```

읽는 법: desired > current 구간 = 노드 자원 부족으로 파드를 못 띄우는 상태

---

### #8 CPU 사용률 per node

**왜:** "워커노드 1 CPU가 100%에 도달했기 때문에 Pending이 발생했다" — 원인 설명

```promql
# 온프레미스 워커노드별 CPU 사용률
1 - avg by (instance) (
  rate(node_cpu_seconds_total{mode="idle", env="onprem"}[1m])
)

# EKS 워커노드별
1 - avg by (instance) (
  rate(node_cpu_seconds_total{mode="idle", env="eks"}[1m])
)
```

### #9 재고 충돌 횟수 (Inventory Service 전용)

**왜:** 동시 주문 폭증 시 `SELECT FOR UPDATE` 충돌이 실제로 몇 번 발생했는지 직접 측정

```promql
# 온프레미스
rate(inventory_stock_conflicts_total{env="onprem"}[1m])

# EKS
rate(inventory_stock_conflicts_total{env="eks"}[1m])
```

### #10 결제 처리 건수 (Payment Service 전용)

**왜:** 시나리오 3 장애 중 실제로 몇 건의 결제가 성공/실패했는지 직접 측정

코드에서 `paymentTotal.inc({ status: payStatus })`로 `status` 레이블이 있으므로 성공/실패 분리 필수.

```promql
# 온프레미스 — 성공 (PAID)
rate(payment_processed_total{status="PAID", env="onprem"}[1m])

# 온프레미스 — 실패 (FAILED)
rate(payment_processed_total{status="FAILED", env="onprem"}[1m])

# EKS — 성공
rate(payment_processed_total{status="PAID", env="eks"}[1m])

# EKS — 실패
rate(payment_processed_total{status="FAILED", env="eks"}[1m])
```

> Grafana 패널에서 성공(초록) / 실패(빨강) 두 선을 겹쳐 그리면  
> 장애 구간에서 "성공 급감 + 실패 급증"이 한눈에 보임.

### #11 API 엔드포인트별 P95 응답시간

**왜:** `/api/products`와 `/api/orders` 중 어디서 병목이 먼저 발생하는지 특정

```promql
# 온프레미스 — 엔드포인트별 분리
histogram_quantile(0.95,
  sum by (route, le) (
    rate(gateway_http_duration_seconds_bucket{
      env="onprem",
      route=~"/api/(products|inventory|orders|payments).*"
    }[1m])
  )
)
```

확인 포인트: 시나리오 2에서 `/api/inventory`(재고)가 먼저 튀는지, `/api/products`(조회)가 먼저인지

### #12 DB Primary / Replica 상태 (DB 페일오버 — 시나리오 4)

**왜:** Primary가 죽고 Replica로 넘어갔는지, 페일오버가 실제로 일어났는지 한눈에

```promql
# 1 = 정상, 0 = 다운
pg_up{env="onprem"}
pg_up{env="eks"}
```

읽는 법: Primary 다운 순간 0으로 떨어짐 → (온프레) 수동 승격 / (EKS) RDS 자동 페일오버 후 1로 회복.

---

### #13 Replication Lag (DB 페일오버 — 시나리오 4)

**왜:** Primary→Replica 복제 지연. 페일오버 순간 이 lag만큼 **데이터 유실 위험**을 정량화

```promql
# 온프레미스 (스트리밍 복제 — lag 존재)
pg_replication_lag_seconds{env="onprem"}

# EKS RDS Multi-AZ는 동기 복제 → lag ≈ 0
pg_replication_lag_seconds{env="eks"}
```

> postgres_exporter 기본에 없으면 커스텀 쿼리 필요:
> `SELECT EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()))` (Replica에서)

---

### #14 DB 페일오버 MTTR ★ (시나리오 4 핵심)

**왜:** "온프레 수동 승격 수 분 vs RDS 자동 60초" — **시나리오 4의 결론 그래프**

```promql
# pg_up이 0인 구간의 길이 = DB 다운타임 (MTTR)
pg_up{env="onprem"}    # 0→1 회복 시각 − 다운 시각 = MTTR
pg_up{env="eks"}
```

> Error Rate(#3) + DB Active Connection(템플릿)을 같이 겹쳐 보면
> **"DB 죽음 → 앱 에러 급증 → 새 Primary 재연결 → 회복"** 흐름이 한 화면에 나옴.
> 온프레는 사람이 `pg_promote` 칠 때까지 0 유지, EKS는 60초 후 자동 1.

## 10. 수집 대상 전체 요약표

> 우리 프로젝트에서 모니터링 대상이 되는 컴포넌트, 수집 도구, 포트, 수집 이유를 한눈에 정리한 표.

| **Payment Service** | prom-client | **4004**/metrics | 서비스별 응답시간, **결제 처리 건수** | 장애 중 실제 결제 손실 건수 측정 — 비즈니스 임팩트 정량화 |

## 11. OpenSearch — 로그 수집 및 에러 원인 분석 *(선택)*

> ⚠️ **선택 — 할지 미정.** 메트릭(Prometheus/Grafana)으로 실험은 충분히 성립한다.
> OpenSearch는 "에러가 **왜** 났는지" 로그 원인까지 파고들 때만 추가하는 보조 도구.

> Prometheus/Grafana가 **WHAT(숫자)**을 보여준다면, OpenSearch는 **WHY(로그)**를 보여준다.  
> Error Rate가 37%로 튀었을 때, 실제로 어떤 에러가 왜 발생했는지 로그로 확인한다.

---

### 역할 분담

| 도구 | 역할 | 보여주는 것 |
|---|---|---|
| Prometheus + Grafana | 메트릭 | Error Rate %, TPS, Pending Pod 수, CPU % |
| OpenSearch + Dashboards | 로그 | 실제 에러 메시지, 에러 발생 시각, 서비스별 로그 |

---

### 구성 방식

```
온프레미스 k8s                        EKS
각 Pod stdout/stderr                  각 Pod stdout/stderr
      │                                     │
Fluent Bit DaemonSet                  Fluent Bit DaemonSet
  env=onprem 레이블 추가               env=eks 레이블 추가
      │                                     │
      └──────────── 로그 전송 ──────────────┘
                          ↓
           Amazon OpenSearch Service (단일 인스턴스)
             인덱스: logs-onprem-YYYY.MM.DD
                     logs-eks-YYYY.MM.DD
                          ↓
           OpenSearch Dashboards
             env 필드로 온프레미스/EKS 필터링
```

**Prometheus와 동일하게 인스턴스 1개로 양쪽 수집.**

### NodePort 할당 (온프레미스 k8s)

| 서비스 | NodePort | 용도 |
|---|:---:|---|
| ingress-nginx | 30080 | 외부 트래픽 진입 |
| gateway 메트릭 | 30400 | Prometheus scrape |
| product 메트릭 | 30401 | Prometheus scrape |
| inventory 메트릭 | 30402 | Prometheus scrape |
| order 메트릭 | 30403 | Prometheus scrape |
| payment 메트릭 | 30404 | Prometheus scrape |
| kube-state-metrics | 30800 | Prometheus scrape |
| worker1 node_exporter | 39101 | EC2 iptables DNAT → KVM VM |
| worker2 node_exporter | 39102 | EC2 iptables DNAT → KVM VM |

> NodePort 30400~30404, 30800은 KVM VM 내부에서만 열려있음.  
> 외부 Prometheus가 접근하려면 K8s EC2 호스트에서 iptables DNAT 포워딩 필요.

### iptables DNAT (K8s EC2 호스트에서)

```bash
MASTER_IP=<master-VM-IP>   # k8s-master VM IP (virsh domifaddr로 확인)

# 앱 메트릭 포워딩 (30400~30404)
for port in 30400 30401 30402 30403 30404; do
  sudo iptables -t nat -A PREROUTING -p tcp --dport $port -j DNAT --to-destination $MASTER_IP:$port
done

# kube-state-metrics 포워딩
sudo iptables -t nat -A PREROUTING -p tcp --dport 30800 -j DNAT --to-destination $MASTER_IP:30800

# MASQUERADE (응답 패킷 라우팅)
sudo iptables -t nat -A POSTROUTING -d 10.149.0.0/16 -j MASQUERADE

# 재시작 후에도 유지
sudo apt install -y iptables-persistent
sudo netfilter-persistent save
```

### worker1/worker2 node_exporter 포워딩

```bash
WORKER1_IP=<worker1-eth0-IP>   # lxc list k8s-worker1 로 확인
WORKER2_IP=<worker2-eth0-IP>
sudo iptables -t nat -A PREROUTING -p tcp --dport 39101 -j DNAT --to-destination $WORKER1_IP:9100
sudo iptables -t nat -A PREROUTING -p tcp --dport 39102 -j DNAT --to-destination $WORKER2_IP:9100
sudo netfilter-persistent save
```

### 워커 노드 메트릭 (KVM VM — node_exporter)

KVM 가상머신은 각 VM에 **node_exporter**를 설치하고, EC2 호스트에서 iptables로 포워딩한다.

```bash
# 각 worker VM에 node_exporter 설치 (:9100)
# EC2 호스트에서 포워딩 (worker1→39101, worker2→39102)
sudo iptables -t nat -A PREROUTING -p tcp --dport 39101 -j DNAT --to-destination <worker1-VM-IP>:9100
sudo iptables -t nat -A PREROUTING -p tcp --dport 39102 -j DNAT --to-destination <worker2-VM-IP>:9100
```

prometheus.yml 추가:
```yaml
- job_name: 'node-onprem'
  static_configs:
    - targets: ['<K8s-EC2-공인IP>:39101', '<K8s-EC2-공인IP>:39102']
  relabel_configs:
    - target_label: env
      replacement: onprem
```

> 주요 메트릭: `node_cpu_seconds_total{mode="idle"}` (CPU), `node_memory_MemAvailable_bytes` (메모리)
> 워커 CPU 패널 PromQL 예: `100 - avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[1m])) * 100`

### k6 → Prometheus 연동

k6가 직접 Prometheus에 remote write로 메트릭 전송. Prometheus 설정:

```yaml
# docker-compose.yml 에 이미 포함됨
command:
  - '--web.enable-remote-write-receiver'  # k6 메트릭 수신
```

k6 실행 시 환경변수:
```bash
K6_PROMETHEUS_RW_SERVER_URL=http://<모니터링-사설IP>:9090/api/v1/write \
BASE_URL=http://<타겟-IP> \
docker compose up
```

상세 사용법은 `msa_shoply/k6/README.md` 참고.
