## k6 스크립트 개요

위치: `msa_shoply/k6/scripts/scenario.js`

```
흐름: 홈 접속 → 로그인(test1~2000 랜덤) → 상품 조회 → 주문 → 결제
부하: 웨이브 방식 (200명씩 누적, 현재 10웨이브 = 2000명)
계정: test1~2000 / 비번 Test1234! (전 계정 동일)
상품: 20개 상품 ID에 분산 (DB 락 경합 줄임)
```

### 부하 방식 — 하이브리드

```
1차: request 100m 작게 → HPA가 쉽게 발동 (실제CPU÷request ≥ 60%)
2차: k6 RPS/VU 크게  → 실제 CPU도 올림
```

> 실험 전 반드시 `msa_shoply/db/load-test-prep.sql` 실행 (재고/주문 리셋).

## 실험 전 재고 초기화 (PostgreSQL 서버)

매 실험(시나리오 A/B/C) 시작 전, **양쪽 환경(온프레미스/EKS)에 동일하게** 재고·주문 데이터를 리셋한다. 안 하면 직전 실험에서 깎인 재고/쌓인 주문이 다음 실험을 오염시킨다.

### 실행 위치 — DB EC2 (PostgreSQL 컨테이너)

```bash
# 1) 맥 → DB EC2 로 SQL 파일 전송 (절대경로)
scp -i ~/key/aws-3tier-keypair.pem \
  ~/shopping_k8s/msa_shoply/db/load-test-prep.sql \
  ubuntu@<DB-EC2-공인IP>:~/postgres/

# 2) DB EC2 접속 후 컨테이너 안에서 실행
ssh ubuntu@<DB-EC2-공인IP>
docker exec -i shoply-postgres psql -U shoply -d shoply < ~/postgres/load-test-prep.sql
```

### SQL이 하는 일 (`msa_shoply/db/load-test-prep.sql`)

```sql
-- 1. k6가 실제로 주문하는 상품 20개 → 재고 5000개로 리셋
--    (시나리오 A 최고 1500 RPS × 주문 30% 기준 — 20분 동안 SKU당 ~2,000건 예상)
UPDATE inventory
SET quantity = 5000, reserved = 0
WHERE product_id IN ( /* k6 시나리오가 쓰는 20개 상품 ID */ );

-- 2. 나머지 상품도 바닥값 확보 (부하 중 품절로 실험 오염 방지)
UPDATE inventory SET quantity = 500, reserved = 0
WHERE quantity < 200 AND product_id NOT IN ( /* 위 20개 제외 */ );

-- 3. 나머지 상품 reserved(예약 수량) 초기화
UPDATE inventory SET reserved = 0
WHERE product_id NOT IN ( /* 위 20개 제외 */ );

-- 4. 거래 흔적 초기화 (이전 실험의 주문/결제 데이터 삭제)
TRUNCATE TABLE payments, order_items, orders CASCADE;

-- 5. 확인 — 상품수/SKU수/k6대상 재고/계정수/주문수(0이어야 정상)를 한 번에 출력
SELECT
  (SELECT COUNT(*) FROM products)  AS 전체상품수,
  (SELECT COUNT(*) FROM inventory) AS 전체SKU수,
  (SELECT MIN(quantity) FROM inventory
     WHERE product_id = '86f68efd-84f7-4630-9c50-4133f95cc67d') AS k6상품1_재고최소,
  (SELECT MIN(quantity) FROM inventory) AS 전체재고최소,
  (SELECT COUNT(*) FROM users)  AS 계정수,
  (SELECT COUNT(*) FROM orders) AS 주문수_초기화확인;
```

> 마지막 `SELECT` 결과에서 **`주문수_초기화확인` = 0**, **`k6상품1_재고최소` = 5000** 이면 정상 리셋된 것.
> 전체 SQL(20개 상품 ID 전문)은 [`msa_shoply/db/load-test-prep.sql`](../../app/db/load-test-prep.sql) 참고.

## 한계치 측정 (실전 방법)

> 부하를 점점 올리면서 "온프레미스가 몇 RPS/VU에서 무너지는지" 찾는 실전 방법.
> 이 숫자가 발표의 핵심 — "온프레미스 한계 = N RPS".

---

## 1. 한계의 정의

**한계 = Pending Pod이 처음 뜨는 지점.**

```
부하 증가 → HPA가 파드 늘림 → 노드 자원 소진
→ HPA는 더 늘리고 싶은데 노드에 자리 없음
→ Pending 발생  ← 여기가 한계 ★
```

> "HPA는 늘리려는데 못 늘린다" = 고정 자원의 한계. 이게 EKS(Karpenter로 노드 추가)와 갈리는 지점.

---

## 2. 한계 도달 신호 3가지

| 신호 | 확인 명령 | 한계? |
|---|---|---|
| Pending 발생 | `kubectl get pods -n shoply --field-selector=status.phase=Pending` | ★ **한계 도달** |
| 워커 CPU 90%+ | `kubectl top nodes` | 거의 다 참 |
| HPA CURRENT = MAX | `kubectl get hpa -n shoply` | 더 못 늘림 |

**Pending이 가장 명확한 신호.** 나머지 둘은 보조.

---

## 3. 측정 방법 — 계단식으로 올리기

한 번에 확 올리지 말고, **단계별로 찍으면서** 올린다.

```
500 VU   → [확인] → CPU? Pending? 파드 수?
1000 VU  → [확인]
2000 VU  → [확인]
4000 VU  → [확인]
...
Pending 뜨는 지점 = 한계
```

### 매 단계 확인 (3개 한 번에)

```bash
# 상태별 파드 수 (Running 몇 개 / Pending 몇 개)
kubectl get pods -n shoply --no-headers | awk '{print $3}' | sort | uniq -c

# 워커 노드 CPU
kubectl top nodes

# HPA 현재 vs 목표
kubectl get hpa -n shoply
```

### Pending만 빠르게

```bash
# Pending 개수
kubectl get pods -n shoply --field-selector=status.phase=Pending --no-headers | wc -l

# NODE가 <none>이면 배치 안 된 것 = Pending
kubectl get pods -n shoply -o wide
```

---

## 4. 역산 — 대략의 한계 예측

선형이라고 가정하면 현재 상태에서 한계를 추정할 수 있다.

```
예) 2000 VU에서 노드 50% 참 (파드 ~20개)
    → 4000 VU에서 100% → Pending 시작 예상

계산: 노드 2개 × 2core = 4000m
      request 100m → 노드당 ~20개 파드
      2노드 = ~40개에서 노드 꽉 참 → Pending
      (시스템 파드 자리 빼면 실제 35~38개)
```

> 선형이 아닐 수 있음(캐시·DB 병목). 역산은 출발점일 뿐, **실제 Pending 뜰 때까지 올려서 확인.**

## 5. 부하 올리는 두 가지 방법

| 방법 | 무엇 | 발표 설명 |
|---|---|---|
| **동시 접속자(VU) 늘리기** | "사람 수" 증가 | ✅ "N명이 동시에 몰리면" — 직관적 |
| 텀(wait) 줄이기 | 1인당 요청 빈도 증가 | 보조 |

둘 다 결국 RPS를 올려 CPU를 더 태우는 것. **VU 늘리기가 설명하기 쉬움.**

### k6 웨이브 늘리는 예시

```js
// 지금: 10웨이브 × 200 = 2000명
// 방법 A — 웨이브 추가 (20웨이브 × 200 = 4000명)
// 방법 B — 웨이브당 인원 키우기 (10웨이브 × 400 = 4000명)
```

## 6. Pending 원인 검증 (중요)

Pending이 떴으면 **"노드 자원 부족"이 진짜 원인인지** 확인한다.

```bash
kubectl describe pod <pending-파드명> -n shoply | grep -A3 Events
```

| Events 메시지 | 의미 |
|---|---|
| `Insufficient cpu` / `Insufficient memory` | ✅ **정답** — 노드 자원 부족 (원하던 그림) |
| `ImagePullBackOff` | ❌ 이미지 못 받음 (다른 문제) |
| `node affinity` 충돌 | ❌ 배치 규칙 문제 (다른 문제) |

→ `Insufficient`가 나와야 "고정 자원 한계"로 측정이 유효하다.

## 6-1. 이벤트 로그 / 증거 캡처 (한계 지점 발견 시 즉시)

> ⚠️ **쿠버네티스 이벤트는 기본 1시간만 보관**되고 사라진다. 한계(Pending) 지점이 나오면 **그 순간 바로** 파일로 저장해야 발표/분석 증거로 남는다.

### 이벤트 로그 보는 법

```bash
# 특정 파드 이벤트 (Pending 원인 등) — describe 맨 아래 Events 섹션이 핵심
kubectl describe pod -n shoply <파드명> | grep -A20 Events

# Pending 파드 전부의 원인 한 번에
for p in $(kubectl get pods -n shoply --field-selector=status.phase=Pending -o name); do
  echo "===== $p ====="; kubectl describe -n shoply $p | grep -A5 Events
done

# HPA 스케일 이벤트 (언제 몇 개로 올렸나/내렸나)
kubectl describe hpa -n shoply product-hpa | grep -A15 Events

# 네임스페이스 전체 이벤트 시간순 ★ 제일 유용
kubectl get events -n shoply --sort-by='.lastTimestamp'
kubectl get events -n shoply -w                                  # 실시간
kubectl get events -n shoply --field-selector type=Warning       # 경고만
```

### 한계 지점 증거 5종 저장 (그 순간 그대로)

```bash
kubectl get events -n shoply --sort-by='.lastTimestamp' > ~/실험_이벤트_$(date +%H%M).txt
kubectl get pods   -n shoply -o wide                    > ~/실험_파드_$(date +%H%M).txt
kubectl get hpa    -n shoply                            > ~/실험_hpa_$(date +%H%M).txt
kubectl describe hpa -n shoply                          > ~/실험_hpa상세_$(date +%H%M).txt
kubectl top nodes                                       > ~/실험_노드_$(date +%H%M).txt
```

→ 타임스탬프 박힌 **"N RPS에서 파드 P개로 한계, Pending Q개, 원인 Insufficient cpu, 워커 CPU XX%"** 증거 확보.

### 실시간 관찰 조합 (터미널 3개)

```bash
watch -n 2 'kubectl get pods -n shoply -o wide | grep -v Running'   # 1: 파드 상태
kubectl get hpa -n shoply -w                                        # 2: HPA REPLICAS/TARGETS
kubectl get events -n shoply -w                                     # 3: 이벤트 흐름
```

> 로그 영구 저장·검색이 필요하면 OpenSearch(Fluent Bit) — **선택 항목**. 핵심 측정은 위 스냅샷 + Prometheus/Grafana로 충분 ([03_모니터링.md](03_모니터링.md) 참고).

## 6-2. 부하 멈춰도 파드가 천천히 줄어드는 이유 (정상)

부하를 멈췄는데 파드가 바로 안 줄고 한참(약 5분) 유지되다 줄어든다 — **고장 아니라 HPA 기본 동작**이다.

| 동작 | 기본 타이밍 |
|---|---|
| 판단 주기 | 15초마다 CPU 확인 |
| 민감도 | 목표 ±10% 안이면 무시 (60% 목표 → 54~66%는 그대로) |
| **올릴 때** | 즉시 (대기 0초), 15초당 +4개 또는 2배 중 큰 쪽 |
| **내릴 때** | **최근 5분(300초) 계속 낮아야** 내림 (`scaleDown.stabilizationWindowSeconds` 기본값) |

> **올릴 땐 공격적 / 내릴 땐 보수적**. 트래픽이 잠깐 출렁여 파드를 줄였다 늘렸다(thrashing) 하는 걸 막는 안전장치라 일부러 느리게 내린다.

실험에서 회복 시간을 빨리 보고 싶으면 `behavior`로 조절 가능 (단 **온프레/EKS 양쪽에 동일 적용**해야 공정):

```yaml
spec:
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60   # 기본 300 → 60초로 단축 예시
```

| 측정 | 값 | 출처 |
|---|---|---|
| 한계 VU | ___ 명 | k6 |
| 한계 RPS | ___ RPS | Grafana 전체 RPS |

| 그때 Pending 파드 | ___ 개 | `uniq -c` |

→ 완성 문장:
> **"온프레미스는 N RPS(M명)에서 Pending P개 발생, Error율 X%로 한계 도달"**

## 8. 측정 흐름 요약

```
1. load-test-prep.sql 실행 (재고/주문 리셋)
2. Grafana 대시보드 띄움 (파드 상태 패널 주목)

7. 기록 템플릿 채움 → 한계(시나리오 2) 데이터 확보
```

## 9. 결과 자동 캡처·리포트 (스크립트)

> 수동으로 `kubectl ... > 파일`을 일일이 찍는 대신, 스크립트 2개로 **자동 캡처 → HTML 리포트**까지.
> 역할 분담: **k8s 진단(서비스별 파드/Pending/실패·로그·노드 할당률)은 스크립트**, **성능(RPS·Error·P95)은 Prometheus/Grafana** — 안 겹친다.

### 스크립트 위치
```
scripts/capture-loop.sh        ← master VM에서 실행 (주기적 자동 스냅샷)
scripts/analyze_experiment.py  ← 맥에서 실행 (스냅샷 → HTML 리포트)
```

### ① 자동 캡처 — capture-loop.sh (master VM)

부하 시작 직전 켜두면 Ctrl+C 할 때까지 주기적으로 스냅샷 저장. **과부하(Pending) 구간이 자동 캡처**되므로 "그 순간"을 손으로 노릴 필요 없음.

```bash
# master VM에 올린 뒤
chmod +x ~/capture-loop.sh
./capture-loop.sh shoply 30      # shoply NS, 30초마다
# 멈춤: Ctrl+C → "파드 최다 스냅샷" 폴더 + 다음 명령 출력
```

매 스냅샷 폴더(`~/실험결과/run_시간/snap_시간/`)에 저장되는 것:

| 파일 | 내용 |
|---|---|
| `요약.txt` | **서비스별 파드 수(status별) + 총/Pending/실패** |
| `진단.txt` | 비정상 파드의 Events + 로그 (왜 안 떴나) |
| `실험_노드할당률.txt` | **노드 CPU request 할당률** (Pending 진짜 원인) |
| `실험_파드.txt` / `실험_파드CPU.txt` | 파드 배치 / 파드별 CPU |
| `실험_노드.txt` / `_hpa.txt` / `_이벤트.txt` | top / HPA / 이벤트 |

> 파일명 시각은 **KST**(스크립트가 `TZ=Asia/Seoul` 고정). VM 기본은 UTC라 안 하면 9시간 어긋남.

### ②-1. 캡처한 run 폴더 맥으로 가져오기 (scp)

capture-loop을 멈추면 master VM의 `~/실험결과/run_시각/`에 다 모여있다. 통째로 맥에:
```bash
# 맥에서 — EC2 경유(ProxyCommand)로 master VM의 run 폴더 전체 가져오기
scp -r -i ~/key/aws-3tier-keypair.pem \
  -o ProxyCommand="ssh -i ~/key/aws-3tier-keypair.pem -W %h:%p ubuntu@<EC2-공인IP>" \
  'ubuntu@<master-VM-IP>:~/result/run_*' \
  ~/shopping_k8s/result/
```
> 원격 경로는 **따옴표**로 감싸야 `run_*` 글롭이 master VM에서 펼쳐진다 (안 그러면 맥에서 펼치려다 실패).
> VM에서 바로 리포트 만들 거면 이 단계 생략 가능 (단 VM엔 브라우저 없어 HTML 자동으로 안 열림).

### ②-2. 리포트 생성 — analyze_experiment.py (맥)

```bash
# run 폴더만 주면 됨 — 한계(파드 최다) 스냅샷을 자동 선택해 HTML 1개 생성
python3 scripts/analyze_experiment.py result/run_XXXX \
  --title "온프레 시나리오2 — 과부하"
```

리포트에 들어가는 것: 요약 배지(한계 도달 여부) · **서비스별 Running/Pending/실패 표** · **진단(원인·로그, 스크롤)** · **노드 할당률** · 노드 사용률 · 서비스별 최대 파드(이벤트 기준) · **타임라인(최신순, 스크롤)** · 결론.

> 해석은 전부 로그 파싱(정규식)이라 **같은 입력 → 같은 결과**(재현성). 온프레·EKS 양쪽에 똑같이 돌려 비교 가능.

### 전체 워크플로 (4단계)

```
1. capture-loop.sh 켜기        (자동으로 순간들 다 저장)
2. k6 부하 계단식 ↑ → Pending 떠도 유지 (과부하 측정)
3. 충분히 모았으면 부하 종료 → Ctrl+C
4. run 폴더 맥에 scp → 파드 최다 snap 폴더에 analyze_experiment.py → HTML
```

## 참고 — 한계가 안 보일 때

| 증상 | 원인 | 조치 |
|---|---|---|
| CPU 낮은데 파드 안 늠 | 부하 약함 | VU 더 올림 |
| 파드 느는데 Pending 안 뜸 | 노드 여유 있음 | VU 더 올림 (한계까지) |
| k6가 목표 RPS 못 만듦 | 부하 생성기 한계 | k6 서버 스펙 ↑ or 분산 |
| Pending 원인이 Insufficient 아님 | 설정 문제 | 이미지/affinity 점검 |
