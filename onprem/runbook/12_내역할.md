## 1. 앱 빌드

쇼핑몰 MSA 7개 서비스의 코드·로직·이미지를 담당.

### 담당 서비스 (7개)

| 서비스 | 포트 | 핵심 역할 |
|---|:---:|---|
| **gateway** | 4000 | 모든 API 진입점. `/api/*`를 각 마이크로서비스로 프록시 + Prometheus 메트릭 수집 |
| **product** | 4001 | 상품 목록/상세 조회. Redis 캐시 (목록 60초, 상세 30초) |
| **inventory** | 4002 | 재고 관리. **SELECT FOR UPDATE 동시성 제어** (reserve/deduct/release) |
| **order** | 4003 | 주문 생성. 재고 예약 → 주문 저장 (트랜잭션) |
| **payment** | 4004 | 결제 처리 (Mock 95% 성공). 성공 시 재고 차감, 실패 시 예약 해제 |
| **user** | 4005 | 로그인/인증 (bcrypt + JWT) |
| **frontend** | 80 | React 쇼핑몰 UI (상품/주문/결제/어드민) |

> 7개 서비스를 **특별한 순서 없이** 작성했다. 백엔드는 Express(TypeScript), 프론트는 React.
> 재고 동시성(`SELECT FOR UPDATE`)으로 동시 주문이 몰려도 초과판매(oversell)가 안 나게 처리.

### 이미지 / 빌드

- 각 서비스 Dockerfile (TypeScript 빌드 → Node 실행)
- **git push → GitHub Actions로 이미지 빌드 → GHCR 자동 푸시** (`ghcr.io/incheon-soda/shoply-*`)
- 아직 코드 틀린 거 확인 수준 (파이프라인 고도화는 아님)
- 빌드 검증: `docker compose build` 전체 통과 확인

## 2. 온프레미스 인프라

AWS EC2 위에 **KVM 가상머신**으로 물리 온프레미스 k8s를 재현.

### EC2 구성

| EC2 | 역할 |
|---|---|
| c8i.2xlarge | k8s 호스트 (KVM VM 3대 + 호스트 Nginx) |
| PostgreSQL EC2 | DB (Docker, PostgreSQL 16, max_connections 300) |
| Redis EC2 | 캐시 (Docker, Redis 7) |

### KVM 가상머신 구축 (실제 과정 — 시행착오 포함)

| 단계 | 내용 |
|---|---|
| **인스턴스** | c8i-flex.2xlarge **스팟** — 인프라 검증 후 끌 거라 온디맨드 불필요 |
| **OS** | Ubuntu **24.04** — 22.04는 스팟 가용성이 없어서 24.04로 (바로 받아짐) |
| **첫 시도 실패** | c8i-flex인데 KVM 가상화 비활성 → 처음엔 **LXD 컨테이너**로 구성 (서비스·부하 잘 돌아감) |
| **의문 → 해결** | "중첩가상화 되는 인스턴스인데 왜 안 되지?" → 찾아보니 **중첩가상화를 활성화**해야 함 |
| **활성화 방법** | 스팟 요청 페이지엔 옵션 없음 → **launch template를 만들어** 중첩가상화 켜니 KVM 작동 |
| **VM 생성** | cloud-init으로 VM 3대 초기화 (master/worker1/worker2, 각 2vCPU/4GB) |
| **k8s 설치** | containerd·kubeadm/kubelet/kubectl 등 **직접 하나씩 설치** (자동화 X), master `kubeadm init` + worker `join` |
| **삽질** | 설치 항목을 하나씩 빠뜨려 재설치 반복. 다음날 정리 파일에도 누락 발견 → 다시 설치+정리 |

> **교훈:** AI 가이드가 "다 한 것 같은데 하나씩 빼먹어서" 설치-재설치를 여러 번 반복.
> 결국 설치 절차를 직접 문서로 고정해서 재현 가능하게 만들었다.

### k8s 클러스터 (실제 진행)

| 단계 | 실제 |
|---|---|
| **init** | master에서 `kubeadm init --pod-network-cidr=10.244.0.0/16 --apiserver-advertise-address=$MASTER_IP` |
| **join** | worker 2대 `kubeadm join <MASTER>:6443 --token ...` (init 출력 복사) |
| **CNI** | Flannel **v0.26.7** (`kubectl apply` GitHub 릴리스) |
| **부가** | metrics-server (`--kubelet-insecure-tls`), Nginx Ingress (helm, NodePort 30080) |
| **노드 라벨** | `kubectl label node ... experiment-role=worker1/worker2` — 파드를 노드별로 고정 배치(affinity) + 어느 파드가 어디 있나 구분 |

> **삽질:** `net.ipv4.ip_forward`를 OS 공통설정에서 빠뜨려 → `kubeadm init` 전에 수동으로 적용해야 했음.

### 네트워크

- **EC2 iptables DNAT** = NAT 포워딩 (KVM VM은 공인IP 없음)
  - `EC2:30080 → DNAT → master_VM:30080` — kube-proxy가 master에도 30080을 열어줘서 동작
- **iptables DNAT 포워딩** — VM 내부 NodePort 메트릭을 외부 Prometheus로 (30400~30404, 30800, 39101/39102)

### 보안

- Security Group / 포트 관리

## 3. 서비스 배포

k8s 매니페스트 작성 및 클러스터 배포.

### 실제 진행

- 매니페스트는 **AI 도움을 받아 작성** (구조 잡고 값 조정)
- 배포는 **막힘 없이 진행** (이미지 pull·CrashLoop·Pending 등 이슈 없었음)
- **ConfigMap DB IP — 처음엔 몰라서 안 넣음.** 인프라를 여러 번 구축하면서
  "여기에 **PostgreSQL/Redis EC2 사설 IP**를 넣어야 파드가 DB에 붙는다"는 걸 깨닫고,
  그 이후부터 ConfigMap에 사설 IP를 채워서 배포 (DB 연결 정상화)

### 매니페스트 구성 (서비스당)

| 리소스 | 역할 |
|---|---|
| Deployment | 파드 정의 (이미지, 리소스, 프로브, affinity) |
| Service (ClusterIP) | 내부 통신 |
| Service (NodePort) | 메트릭 scrape 노출 |
| HPA | 자동 확장 (5개: gateway/product/inventory/order/payment) |
| ConfigMap | DB/Redis 호스트 등 환경값 |
| Secret | DB 비번, JWT, GHCR 인증 |
| Ingress | Nginx 경로 라우팅 (/api→gateway, /→frontend) |

### 확정 설정값

| 항목 | 값 | 이유 |
|---|---|---|
| resource | request **100m** / limit **500m** (frontend 50m/200m) | request 작게 → HPA 민감 발동 |
| HPA | target **60%** 통일, **maxReplicas 99** (replicas 1 시작) | max 제한하면 노드 안 터져 한계 못 봄 → 99로 풀어 Pending 관찰 |
| 배치 | **soft nodeAffinity** (worker1/worker2) | 초기 고정, HPA 추가분은 자유 |
| 인증 | GHCR imagePullSecret | 이미지 pull |

### 배포 검증 (이번에 직접 확인)

- 로그인 흐름: admin(`Admin1234!`)·test1~2000(`Test1234!`) 토큰 발급 ✅
- 주문 → 결제 흐름
- HPA 작동: 부하 주면 파드 증가 ✅

## 4. 실험

온프레미스의 동작·한계·장애 복구를 검증하고 EKS와 비교 분석.

### 시나리오 설계 (안정 → 스파이크 → 장애)

| 시나리오 | 내용 | 보는 것 |
|---|---|---|
| **1 안정** | 200 RPS 정상 | 양쪽 정상 (신뢰 형성) |
| **2 스파이크 ★** | 200 → 1500 급증 후 **유지** | 온프레 Pending 지속 vs EKS 회복 |
| **3 노드장애** | worker1 종료 (전체 worker2로 몰림 → Pending) | MTTR (수동 vs 자동) |
| (4 DB 선택) | Primary DB 종료 | DB 페일오버 (할지 미정) |

### 핵심 실험 노하우 (직접 정립)

| 이슈 | 해결 |
|---|---|
| 깨끗한 앱은 가벼워서 HPA 안 돎 | **하이브리드**: request 100m 작게(HPA 발동) + RPS 크게(CPU↑) |
| 스파이크가 짧으면 반응 전에 끝남 | **급증 + 유지**(5~10분). 유지 구간이 진짜 실험 |
| 재고가 먼저 바닥나면 실험 오염 | `load-test-prep.sql`로 k6 상품 재고 5000개 |
| DB 죽을 때 전 파드 재시작 루프 | liveness/readiness 분리 (`/livez` vs `/health`) |
| 노드 하나로 못 버티는 걸 보여주려면 | 시나리오 3은 **worker1** 종료 → 전체 worker2로 몰림 → Pending |

### 측정 / 분석

- HPA 발동 → Pending 발생 → **한계 RPS** 확인
- EKS 회복 시간 / MTTR 비교
- 결제 실패 건수 = 비즈니스 손실로 환산

### 진행 현황 (실측)

| 항목 | 값 |
|---|---|
| 부하 | 총 **2000명** (k6 `scenario.js` — 10웨이브 × 200명 누적) |
| 파드 | 최대 **60개**까지 증가 |
| 워커 CPU | 최대 **80~90%** |
| 주로 본 패널 | **Running/Pending 숫자, 파드 수 추이** |

- ✅ HPA 작동 확인 (부하 → 파드 60개)
- ✅ Grafana로 Running/Pending·파드 수 실시간 관찰
- ⬜ **한계 RPS 미발견** — CPU 90%까지 갔지만 Pending이 아직 안 떠서 → 부하 더 세게 (예정)
- **다음:** 한계 RPS 찾기 → EKS 동일화 → 시나리오 1/2/3 실행

> **HPA 조정 시행착오:** 처음엔 각 서비스 replicas 2개 + HPA max를 제한해뒀다.
> 그런데 부하를 줘도 **파드가 많이 안 늘고 CPU·메모리도 크게 안 올랐다.**
> → replicas **1개 시작 + max 99**로 풀어서, 노드 한계까지 파드가 늘어 **Pending이 보이도록** 바꿨다.
> (max를 제한하면 노드가 안 터져서 "고정 자원의 한계"를 못 보여주기 때문)

## 전체 흐름에서 내 위치

```
[앱 빌드]        7개 서비스 코드 → Docker 이미지 → GHCR
    ↓
[온프레 인프라]  EC2 → KVM VM 3대 → k8s 클러스터 → 네트워크
    ↓
[서비스 배포]    매니페스트(Deploy/HPA/Ingress) → 클러스터 배포 → 검증
    ↓
[실험]          시나리오 1/2/3 → 한계·MTTR 측정 → 결과 분석
```
