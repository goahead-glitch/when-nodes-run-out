## 🅱️ 시나리오 2 — 스파이크 (순간 급증 + 유지) ★핵심

### ⚠️ 가장 중요한 설계 포인트 — "유지"가 진짜 실험

급증을 짧게(10초) 끝내면 **시스템이 반응하기 전에 끝나서 아무것도 안 보인다.**
- HPA가 파드 늘리는 데 시간 필요
- Karpenter 노드 생성에 **60~90초**

→ **급증은 트리거일 뿐, 차이는 "유지 구간"에서 드러난다.**

### 부하 패턴

```
0~5분:   200 RPS (안정)
5분:     1500 RPS로 급증 (30초~1분에 걸쳐)
5~15분:  1500 RPS 계속 유지  ← ★여기가 진짜 실험 (최소 5분)
```

> 유지 구간이 최소 5분은 돼야 Karpenter 노드 생성·안정화를 관찰할 수 있다.
> 급증 속도가 너무 빠르면(10초) k6/네트워크가 못 따라가 연결거부 에러가 섞일 수 있으니 30초~1분 권장.

### 무슨 일이 일어나나

```
급증 직후 (양쪽 다 잠깐 에러 — 파드/노드가 아직 못 따라옴)
        ↓ 유지하면서 시스템이 반응
온프레: 노드 못 늘림 → Pending 계속 쌓임 → 에러 지속 ──────────
EKS:   Karpenter 노드 추가(60~90초) → 파드 재배치 → 회복 → 에러 0
```

| | 온프레미스 | EKS |
|---|---|---|
| 급증 직후 | Pending 폭발, 에러 급등 | 에러 급등 (동일) |
| **유지 구간** | **계속 Pending / 에러 지속** | **60~90초 후 회복, 에러 0** |
| 목적 | **여기서 갈린다** — 스파이크를 흡수하느냐 못 하느냐 |

### 발표 그림 (이게 핵심 한 장)

```
Error율 (급증 = ⚡)
        ⚡
온프레: ▁▁▁████████████   ← 급증 후 계속 높음 (못 버팀)
EKS:   ▁▁▁███▁▁▁▁▁▁▁▁   ← 급증 후 60~90초 뒤 회복 (흡수)
          5분
```

> **"스파이크를 흡수하느냐 못 하느냐"** — 온프레는 빨간 게 계속, EKS는 잠깐 빨갰다가 초록.

### 측정 포인트 (2개 구간)

| 구간 | 측정 |
|---|---|
| **급증 순간** | 양쪽 에러 피크 (얼마나 튀나) / Pending 첫 발생 |
| **유지 구간** ★ | 온프레: 에러 **지속 시간** & 최대 Pending / EKS: **회복 시간**(Karpenter 노드 뜨고 에러 0까지) & Node Count 증가 |

| 지표 | 온프레미스 | EKS |
|---|---|---|
| 최대 Pending | `kubectl get pods \| grep Pending` | 0 (해소됨) |
| Error율 피크 | Grafana k6 실패율 | (동일) |
| **유지 중 Error** | **계속 높음** | **회복 후 0** |
| Node Count | 2 (고정) | 2→N (Karpenter) |
| EKS 회복 시간 | — | 급증 → 에러 0까지 (60~90초) |

> 온프레 한계가 안 보이면 스파이크 크기 ↑ (1500 → 2000 → ...). 측정 상세 → [04_부하테스트.md](04_부하테스트.md)
> 발표 메시지: *"갑자기 몰리면 — EKS는 흡수하고, 온프레는 계속 무너집니다."*

## 🅲 시나리오 3 — 노드 장애 복구 (MTTR)

```
500 RPS 일정 유지 → 5분 후 worker1 강제 종료
```

worker1 죽으면: Ingress·Gateway·Product·Inventory 죽음 → **모든 파드가 worker2 하나로 몰림**
→ worker2(2core/4GB) 자원 부족 → **Pending → 못 버팀**

| | 온프레미스 | EKS |
|---|---|---|
| 복구 | worker2 하나로 다 안 들어감 → Pending → 수동 복구 (수 분) | Karpenter 새 노드 추가 → 파드 분산 → 자동 (30~60초) |

### 발표 그림

```
Error율 (노드종료 = ✕)
          ✕
온프레: ▁▁▁████████████   ← 사람이 살릴 때까지 다운
EKS:   ▁▁▁███▁▁▁▁▁▁▁▁   ← Karpenter 자동 복구
          5분
```

**측정:**
- MTTR (장애 시작 → 정상 복구)
- 장애 중 결제 실패 건수 (= 비즈니스 손실)

| 지표 | 온프레미스 | EKS |
|---|---|---|
| MTTR | 분 (수동) | ~60초 (자동) |
| 결제 실패 | 건 | 최소 |

> ⚠️ **worker1을 죽이는 이유:** worker1엔 Ingress·Gateway·Product·Inventory가 몰려 있어,
> 죽으면 모든 파드가 worker2 하나로 재스케줄되며 **자원 부족 → Pending**이 극적으로 발생 → "노드 하나로 못 버팀".
> (master는 진입이라 안 죽임. Ingress가 worker2로 재스케줄되며 진입이 잠깐 끊겼다 복구)
> ⚠️ liveness/readiness 분리 필수 — `/livez`(DB 안 봄)=liveness, `/health`(DB 봄)=readiness.

> 발표 메시지: *"복구 시간이 곧 비즈니스 손실입니다 — N분 vs 60초."*

## 2. 진행 순서

```
1. 리허설 — 시나리오 2를 작게 1회 → request/RPS·급증속도 다이얼 확정
2. load-test-prep.sql 실행 + 파드 정상 확인
3. 시나리오 1 (안정) → Grafana 기록
4. DB 리셋 후 시나리오 2 (스파이크) → 급증+유지, 기록 + 스냅샷
5. DB 리셋 후 시나리오 3 (노드 장애 → MTTR)
6. 수치 정리 → 발표 자료
```

## 🅳 시나리오 4 (선택) — DB 페일오버

> **할지 미정 — 여분.** 핵심은 노드 탄력성(2·3)이라 DB는 선택. 여유되면 추가.

```
500 RPS 일정 유지 → Primary DB 강제 종료
```

| | 온프레미스 | EKS |
|---|---|---|
| 복구 | Replica 수동 승격 (`pg_promote`) 수 분 | RDS Multi-AZ 자동 60~120초 |

**앱 대응:** `connectionTimeoutMillis 5000` + `keepAlive`로 죽은 Primary를 빠르게 포기, 새 Primary 재연결.

**측정:** DB MTTR (`pg_up` 0→1) / Replication Lag / 결제 실패 건수

> ⚠️ **liveness/readiness 분리 필수** — `/livez`(DB 안 봄)=liveness, `/health`(DB 봄)=readiness.
> 안 그러면 DB 죽을 때 전 파드가 재시작 루프에 빠져 측정이 망가짐.
> ⚠️ **구성 부담:** Primary-Replica 복제 + 수동 승격 셋업 필요 → 그래서 "선택".
