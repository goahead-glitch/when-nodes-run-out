## 1. 스펙 (버전·저장용량·노드)

| 항목 | 온프레미스 (기준) | EKS (목표) |
|---|---|---|
| **K8s 버전** | v1.34.x (kubeadm 설치) | v1.34.x (eksctl, 동일 마이너) |
| **컨트롤플레인** | master VM에 kubeadm `init` (직접 운영) | AWS 관리형 (EKS) |
| **helm** | nginx-ingress·metrics-server 설치에 사용 | 동일 차트/버전 사용 |
| **HPA (autoscaling/v2)** | target 60%, min 1, max 99 | 동일 |
| **CNI** | Flannel v0.26.7 | AWS VPC CNI (환경 표준 — 측정 안 함) |
| **OS** | Ubuntu **24.04** (KVM **cloud image** + cloud-init) | EKS 최적화 AMI (확정: `___` — Ubuntu EKS AMI로 맞출지 / AL2023로 둘지) |
| **노드 저장용량** | VM당 디스크 `___GB` | 워커 EBS `___GB` (온프레 VM과 동일하게) |
| **DB** | EC2 PostgreSQL 16 (Docker), 저장 `___GB` | RDS PostgreSQL 16, 저장 `___GB` |
| **모니터링 메트릭** | node_exporter(DaemonSet) + kube-state-metrics(Deploy 1) | 동일 구성 |

### 노드 스펙

| | 온프레미스 | EKS |
|---|---|---|
| **호스트** | EC2 **c8i-flex.2xlarge** (8vCPU/16GB, 스팟) 위 KVM | — (워커가 곧 실제 EC2) |
| **마스터** | KVM VM 1대 — 2vCPU/4GB | AWS 관리형 (노드 아님) |
| **워커** | KVM VM 2대 — 각 **2vCPU/4GB** | EC2 **t3.medium** (2vCPU/4GB) × 2 |
| **확장** | ❌ 고정 2워커 | ✅ Karpenter (t3.medium 추가) |

> 워커 1노드 = **2vCPU/4GB** 로 양쪽 동일. 이게 "고정 자원의 한계 vs 탄력 자원" 비교의 전제.

> **OS 이미지 메모:** 온프레는 Ubuntu **cloud image**(`.img`)를 받아 cloud-init으로 VM을 찍어냈다.
> EKS 워커는 instance용 **AMI**를 쓴다 — 커널/OS가 완전히 같진 않지만, vCPU/메모리/리소스 한도가 같으므로 "고정 자원량" 비교 본질은 유지된다.

## 2. Nginx Ingress

| 항목 | 온프레미스 | EKS |
|---|---|---|
| **Ingress Controller** | **Nginx Ingress** (helm) | **Nginx Ingress** (동일) |
| **노출 방식** | NodePort **:30080** | NodePort **:30080** (동일) |
| **라우팅 규칙** | `ingress.yaml` 공유 (`/api`→gateway, `/`→frontend) | **같은 파일 공유** |
| **ALB** | ❌ 안 씀 | ❌ **안 씀** (일부러 안 씀) |

> ⚠️ **ALB를 쓰면 안 된다.** EKS만 LB 종류가 달라지면 트래픽 경로·응답시간이 오염된다.
> LB는 측정 변수가 아니라 **통제 변수** → 양쪽 다 Nginx Ingress NodePort 30080으로 통일.
> kube-proxy가 모든 노드에 30080을 열어주므로 어느 노드로 들어와도 동작한다.

## 3. 트래픽 진입

두 환경의 **유일하게 못 맞추는 경로 차이**. KVM VM은 공인 IP가 없어서 홉이 하나 더 있다.

```
[온프레미스]
  사용자 → EC2 공인IP:30080
            └ iptables DNAT (EC2:30080 → master_VM:30080)   ← 홉 1개 더
              └ Nginx Ingress(NodePort 30080)
                └ 서비스 파드

[EKS]
  사용자 → Worker 공인IP:30080                                ← VM 홉 없음
            └ Nginx Ingress(NodePort 30080)
              └ 서비스 파드
```

| 항목 | 온프레미스 | EKS |
|---|---|---|
| 외부 진입점 | **EC2 공인IP:30080** | **Worker Node 공인IP:30080** |
| VM/노드 전달 | **iptables DNAT** (EC2→master VM) | 없음 (워커가 곧 공인) |
| 진입 후 | Nginx Ingress NodePort 30080 (동일) | Nginx Ingress NodePort 30080 (동일) |

> **보정:** 온프레만 EC2 NAT 홉이 1개 더 있어 절대 응답시간은 약간 불리.
> → 응답시간은 **절대값이 아니라 변화율(%)** 로 비교해 이 차이를 상쇄한다.

## 4. 노드별 서비스 초기 배치

soft nodeAffinity로 **초기 배치만** 고정(`experiment-role` 라벨). HPA가 추가로 띄우는 파드는 자유 배치.

| 노드 | 초기 배치 서비스 |
|---|---|
| **worker1** (`experiment-role=worker1`) | gateway, product, inventory |
| **worker2** (`experiment-role=worker2`) | frontend, order, payment, user |

| 항목 | 온프레미스 | EKS |
|---|---|---|
| 배치 방식 | soft nodeAffinity (worker1/worker2 라벨) | **동일** (라벨링 후 같은 매니페스트) |
| 라벨링 | `kubectl label node ... experiment-role=worker1/2` | 동일 명령 |

> soft(=preferred)라서 노드가 죽으면 다른 노드로 옮겨갈 수 있음 → 시나리오 3(worker1 종료) 때 전부 worker2로 몰려 Pending 발생을 관찰하는 게 목적.

## 5. 리소스 / HPA 설정값

| 항목 | 값 (양쪽 동일) | 이유 |
|---|---|---|
| **request** | 100m / **500m limit** (frontend 50m / 200m) | request를 작게 → HPA가 민감하게 발동 |
| **HPA target** | CPU **60%** (전 서비스 통일) | |
| **minReplicas** | **1** | 1에서 시작해야 증가 폭이 보임 |
| **maxReplicas** | **99** | max를 제한하면 노드가 안 터져 "고정 자원 한계"를 못 봄 |
| **HPA 대상** | gateway / product / inventory / order / payment (5개) | frontend·user 제외 |
| **app DB pool** | max **8** (서비스당) | |

> ⚠️ EKS도 **max 99 그대로**. EKS는 Pending 대신 Karpenter가 노드를 늘려 파드를 다 띄운다 — 그게 비교 포인트.

| 서비스 | 포트 |
|---|:---:|
| frontend (Nginx) | 80 |
| gateway | 4000 |
| product | 4001 |
| inventory | 4002 |
| order | 4003 |
| payment | 4004 |
| user | 4005 |

### 메트릭 노출 (Prometheus가 긁어가는 포트)

| 대상 | 포트 | 비고 |
|---|:---:|---|
| 앱 서비스 `/metrics` | NodePort **30400~30404** | gateway~payment |
| kube-state-metrics | **8080** → NodePort **30800** | 클러스터에 1개 |
| node_exporter | **9100** (노드IP 직접) / NodePort **39101·39102** | 노드마다 1개 |
| Ingress 인바운드 | **30080** | 트래픽 진입 |

> 온프레는 VM이 사설 IP라서 위 NodePort들을 **iptables DNAT**로 외부 Prometheus에 노출. EKS는 워커 공인 IP:NodePort로 직접.

## 7. K8s 구성요소 대조

| 구성요소 | 온프레미스 | EKS | 동일화 |
|---|---|---|---|
| **namespace** | `shoply` | `shoply` | ✅ 같음 |
| **CNI** | Flannel v0.26.7 | AWS VPC CNI | ◻ 환경 표준 (측정 안 함) |
| **Nginx Ingress** | helm, NodePort 30080 | helm, NodePort 30080 | ✅ 같음 |
| **외부 진입 변환** | **iptables DNAT** (EC2→VM) | 워커 공인IP 직접 | ◻ 경로 차이 (3·4 참고) |
| **metrics-server** | 수동 설치 (`--kubelet-insecure-tls`) | EKS 기본 | ✅ 둘 다 있음 |
| **ConfigMap** | DB/Redis 사설 IP 등 환경값 | RDS 엔드포인트로 값만 교체 | ✅ 구조 같음 (값만 환경별) |
| **Secret** | DB 비번·JWT·GHCR 인증 | 동일 (또는 IRSA) | ✅ 같음 |
| **Ingress** | `ingress.yaml` 공유 | 동일 파일 | ✅ 같음 |
| **NodePort** | 30080 / 30400~ / 30800 / 391xx | 동일 | ✅ 같음 |
| **HPA** | target 60 / min 1 / max 99 | 동일 | ✅ 같음 |
| **리소스 값** | 100m / 500m | 동일 | ✅ 같음 |
| **파드 배치** | soft affinity worker1/2 | 동일 | ✅ 같음 |
| **스케줄러** | kube-scheduler 기본 | kube-scheduler 기본 | ✅ 같음 |
| **노드 확장** | ❌ 없음 (고정) | ✅ **Karpenter** | ★ **일부러 다름 (독립변수)** |

### EKS엔 있고 온프레엔 없는 것 → 대체

| EKS 기능 | 온프레 대응 | 처리 |
|---|---|---|
| metrics-server (기본) | 수동 설치함 | 양쪽 있음 ✅ |
| IRSA (IAM Role) | 평문 Secret | 인증 방식만 다름 — 측정 무관 |
| EBS CSI | 외부 DB라 불필요 | 양쪽 외부 DB → 무관 |
| **Karpenter** | **없음 (대체 안 함)** | ★ 이게 비교 대상 — 일부러 안 맞춤 |

## 8. PostgreSQL (EC2 vs RDS)

| 항목 | 온프레미스 (EC2) | EKS (RDS) |
|---|---|---|
| **형태** | EC2 Docker 컨테이너 | RDS 관리형 인스턴스 |
| **버전** | PostgreSQL **16** | PostgreSQL **16** (동일 메이저) |
| **포트** | **5432** | **5432** |
| **max_connections** | **300** | **300** (파라미터그룹으로 맞춤) |
| **저장용량** | `___GB` | `___GB` (온프레와 동일하게) |
| **인스턴스 스펙** | EC2 `___` | RDS `___` (vCPU/메모리 맞춤) |
| **앱 pool max** | 8 (서비스당) | 8 (동일) |
| **자동복구** | ❌ 수동 승격 | ✅ **Multi-AZ 자동** *(시나리오 4 — 선택, 할지 미정)* |

> DB 자동복구(Multi-AZ)는 **선택 항목**. 필수 비교는 노드 확장이고, DB 페일오버(시나리오 4)는 할지 미정.
> 단, `max_connections 300` · 버전 16 · pool max 8 은 **반드시 동일**해야 DB가 변수로 섞이지 않는다.

## 9. 포트 전체 (네트워크 경로)

| 대상 | 포트 | 온프레미스 경로 | EKS 경로 |
|---|:---:|---|---|
| **K8s 인그레스** | 30080 | EC2공인IP → **iptables NAT** → master VM | Worker **공인IP** 직접 |
| **앱 메트릭** | 30400~30404 | VM사설 → iptables DNAT → Prometheus | Worker공인IP:NodePort |
| **kube-state-metrics** | 30800 | iptables DNAT | Worker공인IP:NodePort |
| **node_exporter** | 9100 / 39101·39102 | iptables DNAT | Worker공인IP |
| **PostgreSQL** | 5432 | EC2 사설IP | RDS 엔드포인트 (VPC 내부) |
| **Redis** | 6379 | EC2 사설IP | Redis EC2 공인IP |
| **redis_exporter** | 9121 | EC2 사설IP | EC2 공인IP |
| **postgres_exporter** | 9187 | EC2 사설IP | k8s Pod → NodePort |
| **모니터링 (Grafana)** | 3000 | 별도 EC2 (Prometheus+Grafana) | 동일 EC2 공유 |
| **k6** | — | 부하 발생기 (별도, NodePort/Ingress로 주입) | 동일 스크립트 |

> 핵심 차이는 **"iptables NAT(온프레) vs 공인 IP 직접(EKS)"** 한 줄. 나머지 포트 번호는 전부 동일하게 통일.

## 10. 의도적으로 다르게 두는 것 (독립변수)

이건 강제로 같게 만들면 실험 의미가 사라지는 항목들.

| 항목 | 온프레미스 | EKS | 이유 |
|---|---|---|---|
| **노드 확장** ★ | 고정 2워커 | **Karpenter 자동확장** | ★ 핵심 비교 변수 |
| DB 복구 *(선택)* | EC2 수동 | RDS Multi-AZ 자동 | 시나리오 4 — 할지 미정 |
| 컨트롤플레인 | kubeadm 직접 | AWS 관리형 | EKS 본질 |
| 노드 가상화 | KVM VM (EC2 내부) | 실제 EC2 노드 | 온프레 시뮬레이션 |
| CNI | Flannel | AWS VPC CNI | 각 환경 표준 (측정 안 함) |
| 진입 경로 | EC2 iptables NAT 1홉 | 공인IP 직접 | VM에 공인IP 없음 (변화율%로 보정) |

> **결론:** "관리 편의·진입 경로·가상화"는 못 맞춰도, **'고정 자원 vs 탄력 자원'이라는 비교 본질**은 유지된다.

## 11. 동일화 검증 명령

EKS 구축 후 온프레와 대조해 "공정한 조건" 확인.

```bash
# 버전 / 노드
kubectl version
kubectl get nodes -o wide                    # 워커 2 × 2vCPU/4GB 확인

# 시스템 파드 이미지 버전
kubectl get pod -n kube-system \
  -o jsonpath='{range .items[*]}{.spec.containers[0].image}{"\n"}{end}' | sort -u

# 앱 리소스 / HPA가 온프레와 같은지
kubectl get deploy -n shoply \
  -o custom-columns='NAME:.metadata.name,CPU_REQ:.spec.template.spec.containers[0].resources.requests.cpu'
kubectl get hpa -n shoply                    # target 60 / min 1 / max 99

# 인그레스 / 포트
kubectl get svc -n ingress-nginx             # NodePort 30080 확인
kubectl get ingress -n shoply

# DB
psql -h <RDS-엔드포인트> -U shoply -c "SHOW max_connections;"   # 300
```

→ 위 값들이 온프레미스와 일치하면 **"노드 확장만 다른 공정한 비교 조건"** 확보.

### Karpenter NodePool (EKS 전용, 온프레 스펙으로 확장)

```yaml
requirements:
  - key: node.kubernetes.io/instance-type
    operator: In
    values: ["t3.medium"]   # 2vCPU/4GB = 온프레 VM과 동일
limits:
  cpu: 16                    # 최대 8노드 (비용 보호)
```

## 산출물 (EKS 구축 시)

```
1. k8s/eks/ 오버레이 (configmap-patch: RDS 엔드포인트, karpenter-nodepool)
2. Nginx Ingress 매니페스트 (k8s/common/ingress.yaml 공유)
3. EKS 구축 순서 가이드 (eksctl)
4. 위 §1~§9 비교표를 실측값으로 채워 "동일화 완료" 증명
5. 동일 시나리오(1/2/3) 실행 → 결과 비교
```
