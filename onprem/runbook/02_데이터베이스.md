## 1. DB 구성 개요

### 환경별 구성

| 항목 | 온프레미스 | EKS |
|------|-----------|-----|
| **PostgreSQL** | 별도 EC2 (t3.medium) + Docker | AWS RDS (db.t3.medium) |
| **Redis** | 별도 EC2 (t3.micro) + Docker | 별도 EC2 (t3.micro) + Docker |

> Redis는 양쪽 모두 EC2 Docker로 동일하게 구성 — **통제 변수 (비교 대상 아님)**  
> PostgreSQL만 온프레미스(직접 관리) vs EKS(RDS 관리형)으로 차이를 둔다

### PostgreSQL 역할

모든 서비스가 **하나의 PostgreSQL 인스턴스**를 공유하되, 테이블 소유권은 서비스별로 분리된다.

| 서비스 | 소유 테이블 | 접근 방식 |
|--------|------------|----------|
| User | `users` | SELECT (로그인 시 1회) |
| Product | `products` | SELECT 다수, UPDATE (타임세일) |
| Inventory | `inventory` | **SELECT FOR UPDATE · UPDATE** (동시성 핵심) |
| Order | `orders`, `order_items` | INSERT, SELECT |
| Payment | `payments` | INSERT, UPDATE |

### Redis 역할

Product Service 전용 캐시. **재고(inventory)는 절대 캐시하지 않는다.**

```
상품 목록 조회 → Redis HIT  → DB 쿼리 없이 즉시 반환
               → Redis MISS → DB SELECT → Redis 저장 → 반환

재고 조회      → 항상 PostgreSQL 직접 조회 (캐시 없음)
```

### users

> User Service 소유. 회원 정보 저장.

```sql
CREATE TABLE IF NOT EXISTS users (
  id         UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
  email      VARCHAR(255) UNIQUE NOT NULL,
  password   VARCHAR(255) NOT NULL,    -- bcrypt(cost=10) 해시값
  name       VARCHAR(255) NOT NULL,
  created_at TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);
```

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID | PK, `gen_random_uuid()` 자동 생성 |
| email | VARCHAR(255) | UNIQUE 제약 — 중복 가입 방지 |
| password | VARCHAR(255) | bcrypt 해시 (평문 저장 절대 불가) |
| name | VARCHAR(255) | 표시 이름 |
| created_at | TIMESTAMPTZ | 가입 시각 |

---

### products

> Product Service 소유. 상품 정보 + 타임세일 상태 저장.

```sql
CREATE TABLE IF NOT EXISTS products (
  id           UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
  name         VARCHAR(255) NOT NULL,
  price        INTEGER      NOT NULL,       -- 정상가 (원 단위)
  description  TEXT,
  image_url    VARCHAR(500),
  is_timesale  BOOLEAN      NOT NULL DEFAULT FALSE,
  sale_price   INTEGER,                     -- 세일가 (NULL = 세일 아님)
  sale_ends_at TIMESTAMPTZ,                 -- 세일 종료 시각 (NULL = 세일 아님)
  created_at   TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);
```

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID | PK |
| name | VARCHAR(255) | 상품명 (영문) |
| price | INTEGER | 정상가 (단위: 원) |
| description | TEXT | 상품 설명 |
| image_url | VARCHAR(500) | 이미지 URL |
| is_timesale | BOOLEAN | 타임세일 진행 여부 |
| sale_price | INTEGER | 세일 적용 가격. NULL이면 정상가로 노출 |
| sale_ends_at | TIMESTAMPTZ | 세일 종료 시각. 이 시각 이후엔 자동 만료 처리 |

**타임세일 로직:**
- `is_timesale = TRUE` + `sale_price` + `sale_ends_at` 세 가지가 동시에 설정됨
- 타임세일 종료 시 `is_timesale = FALSE`, `sale_price = NULL`, `sale_ends_at = NULL`으로 복구

### inventory

> Inventory Service 소유. **실험의 핵심 병목 테이블.**

```sql
CREATE TABLE IF NOT EXISTS inventory (
  id         UUID    PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id UUID    NOT NULL REFERENCES products(id),
  size       INTEGER NOT NULL,     -- 신발 사이즈 (240, 250, 260, 270, 280, 290)
  quantity   INTEGER NOT NULL DEFAULT 0,   -- 실제 보유 재고
  reserved   INTEGER NOT NULL DEFAULT 0,   -- 결제 대기 중 예약 수량
  version    INTEGER NOT NULL DEFAULT 0,   -- 낙관적 락 버전 (현재 미사용, 확장 대비)
  UNIQUE (product_id, size)
);
```

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID | PK |
| product_id | UUID | FK → products.id |
| size | INTEGER | 신발 사이즈 mm (240~290, 6종) |
| quantity | INTEGER | 실물 재고 수량 |
| reserved | INTEGER | 주문 후 결제 대기 중인 예약 수량 |
| version | INTEGER | 낙관적 락용 버전 (미사용 중, 확장 대비) |

**가용 재고 계산:**
```sql
available = GREATEST(0, quantity - reserved)
```

**재고 상태 분류 (Product Service):**

| 조건 | 상태 표시 |
|------|----------|
| `available = 0` | 품절 |
| `available <= 5` | 재고 부족 |
| `available > 5` | 재고 있음 |

### orders

> Order Service 소유. 주문 헤더 정보.

```sql
CREATE TABLE IF NOT EXISTS orders (
  id            UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id       UUID        REFERENCES users(id),
  status        VARCHAR(20) NOT NULL DEFAULT 'PENDING',
  total_price   INTEGER     NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  paid_at       TIMESTAMPTZ,          -- 결제 완료 시각
  failed_at     TIMESTAMPTZ,          -- 결제 실패 시각
  failed_reason TEXT                  -- 실패 사유
);
```

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID | PK |
| user_id | UUID | FK → users.id |
| status | VARCHAR(20) | `PENDING` / `PAID` / `FAILED` |
| total_price | INTEGER | 주문 총액 (원) |
| paid_at | TIMESTAMPTZ | PAID 전환 시각 (NULL = 미결제) |
| failed_at | TIMESTAMPTZ | FAILED 전환 시각 |
| failed_reason | TEXT | 실패 사유 |

**주문 상태 전이:**
```
생성 → PENDING
         ├── 결제 성공 → PAID
         └── 결제 실패 → FAILED
```

### order_items

> Order Service 소유. 주문 상세 항목.

```sql
CREATE TABLE IF NOT EXISTS order_items (
  id           UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id     UUID         NOT NULL REFERENCES orders(id),
  product_id   UUID         NOT NULL,
  product_name VARCHAR(255) NOT NULL,    -- 주문 시점 상품명 스냅샷
  size         INTEGER      NOT NULL,
  quantity     INTEGER      NOT NULL,
  unit_price   INTEGER      NOT NULL    -- 주문 시점 가격 스냅샷
);
```

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID | PK |
| order_id | UUID | FK → orders.id |
| product_id | UUID | 상품 UUID (products 테이블 직접 FK 없음 — 서비스 분리 원칙) |
| product_name | VARCHAR(255) | 주문 당시 상품명 스냅샷 (이후 상품명 변경 무관) |
| size | INTEGER | 선택 사이즈 |
| quantity | INTEGER | 수량 |
| unit_price | INTEGER | 주문 당시 단가 스냅샷 |

### payments

> Payment Service 소유. 결제 처리 결과.

```sql
CREATE TABLE IF NOT EXISTS payments (
  id            UUID        PRIMARY KEY DEFAULT gen_random_uuid(),

  method        VARCHAR(20) NOT NULL DEFAULT 'card',  -- card | bank
  status        VARCHAR(20) NOT NULL,                 -- PAID | FAILED

);
```

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID | PK |
| order_id | UUID | FK → orders.id |
| method | VARCHAR(20) | `card` / `bank` |
| status | VARCHAR(20) | `PAID` / `FAILED` |
| amount | INTEGER | 결제 금액 (원) |
| failed_reason | TEXT | `PAYMENT_GATEWAY_ERROR` / `INSUFFICIENT_STOCK` / `INVENTORY_DEDUCT_FAILED` |

## 4. 인덱스 전략

```sql
-- 재고 조회 (product_id로 size별 재고 조회 — 가장 빈번)
CREATE INDEX idx_inventory_product_id  ON inventory(product_id);

-- 주문 상세 조회 (order_id로 items 조회)
CREATE INDEX idx_order_items_order_id  ON order_items(order_id);

-- 주문 상태 필터 (status별 집계 쿼리)
CREATE INDEX idx_orders_status         ON orders(status);

-- 사용자별 주문 조회
CREATE INDEX idx_orders_user_id        ON orders(user_id);

-- 결제 내역 조회 (order_id로 payment 조회)
CREATE INDEX idx_payments_order_id     ON payments(order_id);

-- 타임세일 상품 필터 (is_timesale = TRUE 조회 — 어드민 페이지, 캐시 무효화 후)
CREATE INDEX idx_products_is_timesale  ON products(is_timesale);
```

| 인덱스 | 사용 쿼리 | 효과 |
|--------|----------|------|
| `idx_inventory_product_id` | `WHERE product_id = $1 AND size = $2` | 재고 예약/차감 시 행 빠른 탐색 |
| `idx_products_is_timesale` | `WHERE is_timesale = TRUE` | 타임세일 시작 후 목록 캐시 미스 시 풀스캔 방지 |
| `idx_orders_status` | `WHERE status = 'PENDING'` | 미결제 주문 집계 |
| `idx_payments_order_id` | `WHERE order_id = $1` | 결제 상태 조회 |

## 5. 서비스별 핵심 쿼리

### User Service

```sql
-- 로그인 (email로 사용자 조회 → bcrypt 검증)
SELECT id, email, password, name
FROM users
WHERE email = $1;

-- 회원가입
INSERT INTO users (email, password, name)
VALUES ($1, $2, $3)
RETURNING id, email, name;
```

### Product Service

```sql
-- 상품 목록 (Redis 캐시 미스 시)
SELECT p.id, p.name, p.price, p.description, p.image_url,
       p.is_timesale, p.sale_price, p.sale_ends_at,
       COALESCE(SUM(GREATEST(0, i.quantity - i.reserved)), 0) AS total_available
FROM products p
LEFT JOIN inventory i ON i.product_id = p.id
GROUP BY p.id
ORDER BY p.created_at DESC;

-- 타임세일 시작 (무작위 N개 선택, 할인율 적용)
UPDATE products
SET is_timesale  = TRUE,
    sale_price   = ROUND(price * (1 - $1 / 100.0)),
    sale_ends_at = NOW() + ($2 || ' hours')::INTERVAL
WHERE id IN (
  SELECT id FROM products
  WHERE is_timesale = FALSE
  ORDER BY RANDOM()
  LIMIT $3
);

-- 타임세일 전체 종료
UPDATE products
SET is_timesale  = FALSE,
    sale_price   = NULL,
    sale_ends_at = NULL
WHERE is_timesale = TRUE;
```

### Inventory Service

```sql
-- 가용 재고 조회
SELECT
  SUM(GREATEST(0, quantity - reserved)) AS available,
  SUM(quantity)                         AS total,
  SUM(reserved)                         AS reserved
FROM inventory
WHERE product_id = $1;

-- 재고 예약 (SELECT FOR UPDATE — 아래 6절에서 상세 설명)
BEGIN;
SELECT quantity, reserved FROM inventory
WHERE product_id = $1 AND size = $2
FOR UPDATE;
-- available 검증 후
UPDATE inventory
SET reserved = reserved + $3
WHERE product_id = $1 AND size = $2;
COMMIT;

-- 재고 실차감 (결제 성공 시)
UPDATE inventory
SET quantity = quantity - $3,
    reserved = reserved - $3
WHERE product_id = $1 AND size = $2;

-- 재고 예약 해제 (결제 실패 시)
UPDATE inventory
SET reserved = reserved - $3
WHERE product_id = $1 AND size = $2;
```

### Order Service

```sql
-- 주문 생성
INSERT INTO orders (user_id, status, total_price)
VALUES ($1, 'PENDING', $2)
RETURNING id;

-- 주문 상세 항목 삽입
INSERT INTO order_items (order_id, product_id, product_name, size, quantity, unit_price)
VALUES ($1, $2, $3, $4, $5, $6);

-- 주문 + items 조회 (Payment Service가 호출)
SELECT o.id, o.status, o.total_price,
       json_agg(json_build_object(
         'product_id',   oi.product_id,
         'product_name', oi.product_name,
         'size',         oi.size,
         'quantity',     oi.quantity
       )) AS items
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.id = $1
GROUP BY o.id;

-- 주문 상태 업데이트
UPDATE orders
SET status    = $2,
    paid_at   = CASE WHEN $2 = 'PAID'   THEN NOW() END,
    failed_at = CASE WHEN $2 = 'FAILED' THEN NOW() END,
    failed_reason = $3
WHERE id = $1;
```

### Payment Service

```sql
-- 결제 저장
INSERT INTO payments (id, order_id, method, status, amount, failed_reason)
VALUES ($1, $2, $3, $4, $5, $6);

-- 실시간 통계 (Redis 캐시 미스 시, 3초 TTL)
SELECT
  COUNT(*)::int                                   AS total,
  COUNT(*) FILTER (WHERE status = 'PAID')::int   AS success,
  COUNT(*) FILTER (WHERE status = 'FAILED')::int AS failed
FROM payments;

-- 최근 15건 결제 내역
SELECT
  p.created_at                                                  AS time,
  oi.product_name                                               AS product,
  oi.size::text                                                 AS size,
  CASE WHEN p.status = 'PAID' THEN 'SUCCESS' ELSE 'FAILED' END AS status,
  p.failed_reason                                               AS reason
FROM payments p
LEFT JOIN LATERAL (
  SELECT product_name, size FROM order_items
  WHERE order_id = p.order_id ORDER BY id LIMIT 1
) oi ON true
ORDER BY p.created_at DESC
LIMIT 15;
```

## 6. 동시성 처리 — SELECT FOR UPDATE

### 왜 필요한가

타임세일 시 수백 명이 동시에 동일 상품·사이즈에 주문을 넣으면,  
재고 확인 → UPDATE 사이에 다른 트랜잭션이 끼어들어 **재고 초과 판매**가 발생한다.

```
[동시 요청 100개]
T1: SELECT quantity=10, reserved=8 → available=2 → UPDATE reserved=9
T2: SELECT quantity=10, reserved=8 → available=2 → UPDATE reserved=9  ← 동시에 읽어서 같은 값
결과: reserved=9 (2번 실행됐지만 9로 덮어씀) → 데이터 불일치
```

### SELECT FOR UPDATE 동작

```sql
BEGIN;

-- 해당 행에 배타적 락(X-Lock) 획득
-- 다른 트랜잭션은 COMMIT 전까지 이 행을 읽거나 수정할 수 없음
SELECT quantity, reserved
FROM inventory
WHERE product_id = $1 AND size = $2
FOR UPDATE;

-- 가용 재고 검증
-- available = GREATEST(0, quantity - reserved)
-- available < 요청수량이면 ROLLBACK → 409 반환

-- 예약 수량 증가
UPDATE inventory
SET reserved = reserved + $3
WHERE product_id = $1 AND size = $2;

COMMIT;  -- 락 해제 → 다음 대기 트랜잭션이 락 획득
```

### 실험에서의 의미

```
동시 요청 급증
    ↓
SELECT FOR UPDATE 락 대기 누적
    ↓
DB 커넥션 큐 포화
    ↓
응답 시간 급증 (P95 Latency)
    ↓
timeout → 5xx Error Rate 상승
```

이 과정이 **온프레미스에서 더 심각**하게 나타난다:
- 온프레미스: 파드 수 제한 → 동시 처리 커넥션 수 제한 → 락 대기 길어짐
- EKS: Karpenter 노드 추가 → 파드 증가 → 커넥션 풀 확장 → 락 대기 분산

## 7. Redis 캐싱 구조

### 캐시 키 목록

| 키 패턴 | TTL | 저장 내용 | 무효화 시점 |
|---------|-----|----------|------------|
| `products:list` | 60s | 전체 상품 목록 (total_available 포함) | 타임세일 시작/종료 시 즉시 DEL |
| `products:{uuid}` | 30s | 상품 상세 | 타임세일 시작/종료 시 즉시 DEL |
| `stats:realtime` | 3s | 결제 통계 (total/success/failed/rate/recent15) | 결제 처리 완료 시 즉시 DEL |

### 캐시 히트/미스 흐름

```
GET /api/products
  → redis.get('products:list')
      ↓ HIT  → JSON.parse → 즉시 반환 (DB 쿼리 0)
      ↓ MISS → DB SELECT (JOIN inventory) → redis.setex(60) → 반환

POST /api/products/timesale/start (타임세일 시작)
  → DB UPDATE (products)
  → redis.del('products:list')        ← 즉시 무효화
  → redis.del('products:{id}') × N개  ← 변경된 상품 모두 무효화
```

### 재고는 절대 캐시하지 않는 이유

```
재고 캐시 HIT → 실제 재고와 다른 값 반환
             → available 검증 오류
             → 초과 예약 or 재고 있는데 품절 표시
             → 실험 결과 오염 (SELECT FOR UPDATE 의미 없어짐)
```

### 1. Docker 설치

```bash
sudo apt update && sudo apt install -y docker.io

```

### 2. schema.sql, seed.sql 전송

```bash
# 로컬 Mac에서 실행
scp -i ~/key/aws-3tier-keypair.pem \
  ~/shopping_k8s/msa_shoply/db/schema.sql \
  ~/shopping_k8s/msa_shoply/db/seed.sql \
  ubuntu@<PostgreSQL-EC2-공인IP>:~/
```

### 3. PostgreSQL 컨테이너 실행

```bash
# PostgreSQL EC2에서 실행
docker run -d \
  --name postgres \
  --restart always \
  -e POSTGRES_DB=shoply \
  -e POSTGRES_USER=shoply \
  -e POSTGRES_PASSWORD=shoply1234 \
  -v postgres_data:/var/lib/postgresql/data \

  -v ~/seed.sql:/docker-entrypoint-initdb.d/02_seed.sql \

  postgres:16-alpine
```

> `docker-entrypoint-initdb.d/`에 마운트된 `.sql` 파일은  
> 컨테이너 **최초 기동 시 한 번만** 자동 실행된다.  
> 볼륨에 데이터가 이미 있으면 실행되지 않음.

### 4. 데이터 적재 확인

### 스키마 + 시드 데이터 적용

RDS는 VPC 내부에서만 접근 가능하므로 EKS Worker Node 또는 Bastion에서 실행한다.

```bash

psql -h <RDS-엔드포인트> -U shoply -d shoply \
  -c "SELECT COUNT(*) FROM products;"
# 500개 확인
```

### EKS ConfigMap에 엔드포인트 입력

`msa_shoply/k8s/eks/configmap-patch.yaml` :

```yaml
POSTGRES_HOST: "shoply-db.xxxx.ap-northeast-2.rds.amazonaws.com"
POSTGRES_PORT: "5432"
REDIS_HOST: "<Redis-EC2-사설IP>"
REDIS_PORT: "6379"
```

### RDS 보안그룹 설정

| 방향 | 포트 | 소스 | 이유 |
|------|------|------|------|
| 인바운드 | 5432 | Worker Node SG | k8s 파드 → RDS |

> postgresql_exporter는 EKS 내부 Pod으로 배포 → RDS 접근 후 NodePort 노출  
> Prometheus는 Worker Node NodePort를 scrape

### 온프레미스 vs RDS 차이

| 항목 | 온프레미스 (Docker EC2) | EKS (RDS) |
|------|----------------------|-----------|
| 장애 복구 | 수동 재시작 필요 | Multi-AZ 자동 페일오버 |
| 백업 | 직접 설정 | 자동 백업 |
| max_connections | `postgresql.conf` 수동 수정 | RDS 파라미터 그룹으로 관리 |
| 패치/업그레이드 | 직접 | AWS 자동 (유지 관리 창) |
| 모니터링 | node_exporter + pg_exporter | CloudWatch + pg_exporter |

## 13. 관리 쿼리 모음

### 재고 현황

```sql
-- 전체 재고 현황 요약
SELECT
  COUNT(*)                                      AS total_rows,
  SUM(quantity)                                 AS total_quantity,
  SUM(reserved)                                 AS total_reserved,
  SUM(GREATEST(0, quantity - reserved))         AS total_available,
  COUNT(*) FILTER (WHERE quantity - reserved <= 0) AS out_of_stock
FROM inventory;

-- 상품별 재고 상태 (가용 재고 기준)
SELECT
  p.name,
  SUM(i.quantity)                         AS total_qty,
  SUM(i.reserved)                         AS total_reserved,
  SUM(GREATEST(0, i.quantity - i.reserved)) AS available
FROM products p
JOIN inventory i ON i.product_id = p.id
GROUP BY p.id, p.name
ORDER BY available ASC
LIMIT 20;
```

### 타임세일 현황

```sql
-- 현재 진행 중인 타임세일
SELECT id, name, price, sale_price,
       ROUND((1 - sale_price::numeric / price) * 100) AS discount_pct,
       sale_ends_at
FROM products
WHERE is_timesale = TRUE
ORDER BY sale_ends_at;

-- 타임세일 강제 전체 종료
UPDATE products
SET is_timesale = FALSE, sale_price = NULL, sale_ends_at = NULL
WHERE is_timesale = TRUE;
```

### 결제 통계

```sql
-- 전체 결제 성공률
SELECT
  COUNT(*)::int                                   AS total,
  COUNT(*) FILTER (WHERE status = 'PAID')::int   AS paid,
  COUNT(*) FILTER (WHERE status = 'FAILED')::int AS failed,
  ROUND(
    COUNT(*) FILTER (WHERE status = 'PAID') * 100.0 / NULLIF(COUNT(*), 0),
    1
  )                                               AS success_rate_pct
FROM payments;

-- 실패 사유별 분류
SELECT failed_reason, COUNT(*) AS cnt
FROM payments
WHERE status = 'FAILED'
GROUP BY failed_reason
ORDER BY cnt DESC;

-- 시간대별 결제 건수 (1분 단위)
SELECT
  date_trunc('minute', created_at) AS minute,
  COUNT(*) FILTER (WHERE status = 'PAID')   AS paid,
  COUNT(*) FILTER (WHERE status = 'FAILED') AS failed
FROM payments
GROUP BY 1
ORDER BY 1;
```

### DB 커넥션 모니터링

```sql
-- 현재 활성 커넥션 수 (실험 중 DB 부하 확인)
SELECT COUNT(*), state
FROM pg_stat_activity
WHERE datname = 'shoply'
GROUP BY state;

-- 락 대기 중인 쿼리 (SELECT FOR UPDATE 병목 확인)
SELECT pid, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
  AND datname = 'shoply';

-- 가장 느린 쿼리 Top 10
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database WHERE datname = 'shoply')
ORDER BY mean_exec_time DESC
LIMIT 10;
```
