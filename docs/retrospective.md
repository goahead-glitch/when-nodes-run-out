## 1. 재실험 다시 보기 — 최종 발표 근거로 쓴 숫자는 t3 기록이었다

최종 발표는 실행 ③(EKS 실험 노드를 c8i-flex.large로 바꾼 재실험)의 근거로 **"노드 9대 · 포화 노드 없음 · 클러스터 CPU 최대 90.83%"**를 썼습니다. 팀원 캡처([`karpenter-node-scaling.png`](../team/eks-service/karpenter-node-scaling.png))에도 9대가 c8i-flex.large로 표시돼 있습니다.

그런데 같은 장면의 **원본 EC2 콘솔 캡처**([`eks-9nodes-t3medium-console.png`](images/eks-9nodes-t3medium-console.png))를 보면 9대가 **전부 t3.medium**입니다.

| | 원본 콘솔 캡처 | 발표용 캡처 |
|---|---|---|
| 인스턴스 ID 9개 | `i-0a2bc0712ed641b29` 외 8개 | **같은 ID 9개** |
| 인스턴스 타입 | api 4 · service 4 · ops 1 — **전부 t3.medium** | api · service는 c8i-flex.large, ops만 t3.medium |

EC2는 실행 중에 인스턴스 타입이 바뀌지 않고, 타입을 바꾸면 노드가 새로 만들어져 ID도 달라집니다. 따라서 이 9대는 **t3.medium**이었고, "9대 · 포화 없음 · 90.83%"는 **c8i 재실험이 아니라 t3 때 EKS 테스트의 기록**입니다(같은 세션의 HPA · `kubectl top nodes` 캡처도 같은 시점). 최종 발표 본문에도 "t3.medium 9개"라는 문구가 남아 있었습니다.

같은 t3 세션에서 노드가 9대까지 늘어난 뒤에도 **gateway 파드가 Pending**인 캡처가 있습니다([`eks-pods-pending.png`](images/eks-pods-pending.png)) — 노드를 늘려도 Pending이 계속 생겼다는 뜻이고, 아래 2장의 원인 6번(리소스 낭비)과 같은 방향입니다.

**c8i 재실험(실행 ③) 자체는 했습니다.** launch template을 c8i-flex.large로 바꾼 캡처가 있습니다([`eks-launch-template-c8i.png`](images/eks-launch-template-c8i.png)). 결과는 **초반 몰림 구간에서는 EKS가 온프레보다 먼저 Pending이 났고, 후반에는 노드가 늘면서 안정**됐습니다. 다만 이 재실험의 대시보드 캡처나 수치는 남아 있지 않아, 이 결과는 실험 당시 관찰한 기억에 근거합니다.

> 정리하면, 장비를 c8i로 맞춘 뒤에도 **초반에는 EKS가 먼저 흔들렸습니다.** 장비 차이만으로는 설명되지 않는 원인이 남아 있었다는 뜻이고, 그 원인을 아래에서 정리했습니다.

## 2. 첫 비교는 왜 기대와 다르게 나왔나

프로젝트가 끝난 뒤, 실행 ②의 결과를 다시 뜯어보며 원인을 정리했습니다. 결과 분석 때 찾은 것과, 복기하면서 새로 찾은 것을 함께 적습니다.

### 기대했던 것 vs 실제로 나온 것

고정 자원(온프레)은 노드를 더 늘릴 수 없어 한계에서 무너지고, 탄력 자원(EKS)은 노드를 늘리며 **흔들림 없이** 버틸 것이라고 예상했습니다.

| 항목 | 온프레미스 | EKS | 기대대로였나 |
|---|---|---|---|
| 노드 | 4개 고정 | 3 → 8개 (약 6분에 걸쳐 단계적으로) | ✅ |
| 최종 Running 파드 | 33 | 62 | ✅ EKS가 더 많이 받아냄 |
| Pending | 6~7개가 내려가지 않고 유지 | 최대 12개까지 두 차례 치솟은 뒤 해소 | ⚠ EKS도 Pending이 쌓임 |
| k6 실패율 (전체 집계) | 0.09% | 0.32% | ❌ EKS가 더 높음 |

절반은 기대대로였지만, 확장하는 동안 EKS가 오히려 더 많이 실패했습니다.

### 찾은 원인

| # | 원인 | 언제 찾았나 | 근거 | 확인 정도 |
|---|---|---|---|---|
| 1 | **노드 장비가 달랐다** (EKS t3.medium vs 온프레 c8i-flex) | 첫 발표 후 결과 분석 | 인스턴스 타입 | ⚠ 장비를 맞춘 재실험(실행 ③)에서 후반은 안정됐지만 **초반 Pending은 남음** — 장비 차이만으로는 다 설명되지 않음 |
| 2 | **앱 이미지가 달랐다** (온프레 `:latest` vs EKS `:otel`) | 프로젝트 종료 후 복기 | 양쪽 배포 매니페스트 | ❓ 영향 크기는 검증 못 함 |
| 3 | 노드 증설이 부하 상승보다 느렸다 | 결과 분석 | 비교 캡처 | 캡처로 확인 |
| 4 | EKS가 파드를 훨씬 많이 띄웠다 | 결과 분석 | 200 VU 캡처 | 캡처로 확인 (2번과 연결될 수 있음) |
| 5 | 노드마다 도는 데몬셋 구성이 달랐다 (+ gateway 메모리 request 차이) | 결과 분석 → 복기에서 코드로 대조 | 양쪽 매니페스트 · Terraform · 차트 기본값 | 구성 차이는 코드로 확인, 영향 크기는 미측정 |
| 6 | **리소스 request를 실제 사용량에 맞추지 못해 노드 자원을 버렸다** — 초반 몰림에서 EKS가 먼저 Pending | 프로젝트 종료 후 복기 | 전체 타임라인 캡처 (EKS는 노드 CPU 약 30%에서 Pending 시작, 온프레는 약 80%에서) | 캡처로 확인 |

**1. 노드 장비가 달랐다 — 가장 큰 원인.** 노드 1대 = 2vCPU/4GB로 숫자는 맞췄지만, 실행 ② 당시 EKS 워커는 **t3.medium**(Skylake/Cascade Lake 세대)이었고 온프레 VM은 **c8i-flex**(Intel Xeon 6) 호스트 위에서 돌았습니다. 같은 2vCPU라도 세대가 3세대가량 차이 나서 vCPU 하나가 같은 시간에 처리하는 양이 다릅니다. vCPU·메모리 숫자만 같으면 같은 조건이라고 생각했고, 인스턴스 세대를 통제 변수로 보지 못했습니다. 당시 EKS launch template에 t3.medium이 들어가 있던 캡처: [`run2-eks-launch-template-t3medium.png`](images/run2-eks-launch-template-t3medium.png)

> **CPU 크레딧 제한은 원인이 아니었을 가능성이 큽니다.** t3는 버스터블 인스턴스라 standard 모드에서는 CPU 크레딧을 다 쓰면 기준선(t3.medium은 vCPU당 20%)까지 성능이 깎입니다. 하지만 T3는 따로 지정하지 않으면 **unlimited 모드**로 뜨고, 이 모드에서는 성능이 깎이지 않고 초과 사용분만 요금으로 청구됩니다([AWS T3 안내](https://aws.amazon.com/ec2/instance-types/t3/)). 팀원 Terraform의 launch template에 크레딧 설정이 없으므로, 계정 기본값을 바꾸지 않았다면 unlimited였을 것입니다. 당시 노드의 CloudWatch `CPUSurplusCreditsCharged`(초과 크레딧 청구) 또는 `CPUCreditBalance` 지표로 확인할 수 있습니다.

**2. 앱 이미지가 달랐다 — 복기하면서 새로 찾음.** 온프레 매니페스트(`onprem/k8s/common/`)는 `ghcr.io/ktk026/shoply-*:latest`를, EKS 매니페스트(`team/eks-service/`)는 `ghcr.io/incheon-soda/shoply-*:otel`을 가리키고 있었습니다. `:otel`은 Tempo 트레이싱을 시험해 보려고 OpenTelemetry 계측(`tracing.js`)을 넣어 따로 빌드한 이미지입니다([`cd-otel.yml`](../.github/workflows/cd-otel.yml)). 앱 로직은 같지만 계측이 요청마다 기록을 만들면서 CPU를 더 쓸 수 있고, HPA가 CPU 70% 기준이라 EKS 파드가 더 빨리, 더 많이 늘어나는 쪽으로 작용했을 수 있습니다(4번과 같은 방향). 다만 실험 당일 실제로 떠 있던 이미지와 계측의 CPU 비용은 기록이 없어 영향 크기는 확인하지 못했습니다.

**3. 노드 증설이 부하 상승보다 느렸다.** 부하는 2분마다 100 VU씩 올라 약 4분 만에 300 VU에 도달했지만, EKS 노드는 3개에서 8개가 되기까지 약 6분이 걸렸습니다. 노드가 8개가 된 건 최고 부하 구간이 끝나갈 무렵이었고, 그 사이 늘어난 파드는 Pending으로 쌓여 요청 실패로 이어졌습니다. ([비교 캡처](images/run2-compare-300vu-hold.png))

**4. EKS가 파드를 훨씬 많이 띄웠다.** 같은 HPA 설정(min 2 / max 99)에서 EKS는 파드가 62개까지 늘었고, 새로 생긴 파드는 노드가 붙을 때까지 Pending으로 기다려야 했습니다. 200 VU 단계에서 EKS가 온프레보다 **먼저** Pending을 띄운 것도 이 때문입니다. ([200 VU 캡처](images/run2-stage-200vu.png))

**5. 노드마다 도는 데몬셋 구성이 달랐다.** 서비스 파드의 리소스는 맞췄지만, 노드마다 하나씩 뜨는 파드는 양쪽 코드에서 이렇게 달랐습니다. 값이 코드에 없으면 기본값을 적었습니다.

| 노드마다 뜨는 것 | 온프레 워커 (`onprem/k8s/onprem/`) | EKS 워커 (`team/infra/`) |
|---|---|---|
| CNI | flannel 파드 — 공식 매니페스트 기본 request **100m / 50Mi** | aws-node(VPC CNI) — 차트 기본 request **25m** (메모리 지정 없음) |
| kube-proxy | 파드 — kubeadm 기본, 리소스 지정 없음 | 파드 — EKS 애드온 기본값, 레포·공개 차트로는 확인 불가 |
| node_exporter | **VM에 systemd로 설치 — 파드가 아님** | **DaemonSet 파드** — 차트 기본값 리소스 지정 없음 |
| cAdvisor | DaemonSet, request 50m / 100Mi · limit 150m / 200Mi | 같은 값 |
| Promtail | DaemonSet, request **30m / 64Mi** · limit 100m / 128Mi | Helm 차트 기본값 — **리소스 지정 없음** |

> "리소스 지정 없음"은 스케줄러가 자리를 0으로 계산한다는 뜻입니다. 그만큼 앱 파드가 노드에 더 들어가지만, 실제로는 이 파드들도 CPU를 쓰기 때문에 바쁠 때 같은 노드의 앱 파드와 CPU를 나눠 쓰게 됩니다. 반대로 온프레는 flannel이 100m을 미리 잡아 둡니다. 즉 양쪽의 "앱 파드가 쓸 수 있는 자리"가 서로 다른 방식으로 어긋나 있었습니다.

이 밖에 EKS의 kube-prometheus-stack은 Prometheus Operator를 기본으로 함께 띄우는데(차트 기본 `prometheusOperator.enabled: true`), `values.yaml`에서 끄거나 ops 노드로 보내지 않아 실험 노드에 올라갔을 수 있습니다. 새 노드가 붙을 때마다 데몬셋 파드가 먼저 떠야 해서 증설된 노드가 앱 파드를 받기까지 시간이 더 걸리는 점도 EKS에만 해당합니다. 실험 중 실사용량은 기록이 없어 영향 크기는 측정하지 못했습니다.

> 기본값 출처: flannel `kube-flannel.yml`, aws-vpc-cni · promtail · prometheus-node-exporter · kube-prometheus-stack 차트의 `values.yaml`(2026-11 기준 공개 차트). Terraform에서 promtail · kube-prometheus-stack 차트 버전을 고정하지 않아, 당시 버전의 기본값과 다를 수 있습니다.

**참고 — 앱 파드 리소스 값 대조.** 서비스 파드는 거의 같았지만 두 군데가 달랐습니다.

| 서비스 | 온프레 (`onprem/k8s/common/`) | EKS (`team/eks-service/`) |
|---|---|---|
| gateway | request 100m / **128Mi** · limit 500m / 512Mi | request 100m / **256Mi** · limit 500m / 512Mi |
| product · inventory · order · payment · user | request 100m / 128Mi · limit 500m / 512Mi | 같은 값 |
| frontend | request 50m / 64Mi · limit **200m / 128Mi** | request 50m / 64Mi · limit **50m / 64Mi** |
| HPA | target 70% · min 2 · max 99 · scaleUp 60초당 2개 · scaleDown 15초당 50% | 같은 값 |

gateway는 가장 많이 늘어나는 서비스라, 메모리 request가 두 배면 2vCPU/4GB 노드 하나에 들어가는 gateway 파드 수가 줄어 Pending이 더 빨리 생길 수 있습니다(CPU 기준 약 19개, 메모리 256Mi 기준 약 13개). 다만 실험 중 이 제한에 실제로 걸렸는지는 기록이 없습니다.

**6. 리소스를 너무 버렸다 — 초반 몰림에서 EKS가 먼저 무너진 이유.** 이 실험의 기준은 쇼핑몰이고, 할인·선착순 이벤트라면 트래픽은 **초반에 한꺼번에** 몰립니다. 그런데 실행 ②·③ 모두 EKS는 후반엔 노드가 늘어 안정됐지만, **초반에는 온프레보다 먼저 Pending**이 났습니다.

실행 ② 전체 타임라인 캡처([`run2-compare-full-timeline.png`](images/run2-compare-full-timeline.png))를 보면 차이가 분명합니다.

| | Pending이 처음 생긴 시점 | 그때 노드 CPU |
|---|---|---|
| 온프레 | 약 19:40 (부하 시작 후 약 5분) | 워커 약 80% — 실제로 꽉 찬 뒤 |
| EKS | 약 19:36:40 (부하 시작 후 약 1분 반) | **약 25~35%** — 실제로는 한참 남은 상태 |

EKS는 실제 CPU가 30% 안팎일 때부터 Pending이 났고, 300 VU 구간([`run2-stage-300vu.png`](images/run2-stage-300vu.png))에서도 **노드 CPU 62~70%인데 Pending 8~10개**였습니다. CPU가 남아 있는데도 파드를 더 올리지 못한 것입니다. (EKS 노드별 CPU 패널은 일부 노드만 표시돼 있어, 표의 CPU는 패널에 보이는 노드 기준입니다.)

```
HPA 목표 70%   → 파드는 평균적으로 request의 약 70%만 실제로 씀
스케줄러       → 실제 사용량이 아니라 request 합계로 자리를 계산
결과           → request로는 노드가 100% 찼는데 실제 CPU는 60~70%
               → 남은 30% 남짓은 "예약만 되고 안 쓰이는 자리" = 버려진 자원
```

여기에 EKS 쪽 설정이 겹쳐 자리가 더 빨리 찼습니다.
- gateway 메모리 request 256Mi — CPU가 남아도 메모리 request로 노드가 먼저 "꽉 찬" 것으로 계산됨
- request 없는 데몬셋 · `:otel` 계측 — 실제 CPU를 더 써서 앱 파드 사용률이 올라가고, HPA가 파드를 더 빨리 늘림

노드 자동확장은 **Pending 파드가 생겨야 반응**합니다. 장부상 자리가 일찍 차니 Pending이 일찍 생겼고, 새 노드가 생성 → 클러스터 합류 → 데몬셋 기동 → 이미지 pull을 거쳐 파드를 받기까지의 공백이 초반 몰림 구간과 그대로 겹쳤습니다. **자동확장이 없어서가 아니라, 리소스를 실제 사용량에 맞게 관리하지 못해 이미 가진 노드의 30% 남짓을 놀린 채 Pending을 맞은 것**이 초반에 EKS가 먼저 흔들린 이유입니다.

**영향이 작았을 것으로 보는 차이**
- 데이터 계층: 온프레는 EC2(t3.medium) 위 PostgreSQL, EKS는 RDS(db.t3.medium) — 엔진·버전·사양 등급이 같음
- 진입 경로: 온프레는 MetalLB + 호스트 DNAT로 한 홉이 더 많음 — 오히려 온프레에 불리한 조건이고, Pending·실패보다는 응답 시간에 영향을 주는 차이

### 추정 — 조건을 맞췄다면 얼마나 달랐을까 (측정 아님)

> 아래 숫자는 재실험으로 잰 값이 아니라, 공개 자료와 일반적인 경험치로 잡은 **대략적인 추정**입니다. 원인들의 크기를 가늠해 보려는 목적입니다.

**요소별 예상 영향** (t3.medium 노드 1대 = 1.0 기준)

| 요소 | 예상 차이 | 근거 |
|---|---|---|
| CPU 세대 (t3 vs c8i-flex) | 온프레 vCPU가 약 1.3~1.5배 빠름 | Skylake/Cascade Lake → Xeon 6, 세대마다 대략 10~15%씩 3세대 |
| 온프레 중첩 가상화 | 온프레가 약 5~10% 손해 | EC2 위 KVM VM — 순수 CPU 작업은 손해가 작음 |
| `:otel` 계측 | EKS 파드가 요청당 약 5~20% CPU 추가 사용 | Node.js 자동 계측이 요청마다 스팬 생성, 앱 형태에 따라 편차 큼 |
| 데몬셋 | 양쪽 노드당 약 5% 안팎씩 손해, 서로 상쇄에 가까움 | 에이전트 실사용은 대체로 노드 CPU의 몇 % |
| gateway 메모리 256Mi | 노드가 gateway로만 찬다면 최대 약 30% 덜 들어감 | 실제로는 파드가 섞여 있어 이보다 작음 |

**실제 결과와 맞춰 보기.** HPA는 request 대비 CPU 사용률 70%로 파드를 늘리므로, 같은 요청에 CPU를 더 쓰는 쪽이 파드를 더 띄웁니다.

- EKS 파드가 같은 일에 쓰는 CPU ≈ 세대 1.3~1.5 × otel 1.05~1.2 ÷ 중첩 가상화 0.9~0.95 ≈ **온프레의 약 1.4~1.9배**
- 실제로 띄우려 한 파드 수: 온프레 40개(Running 33 + Pending 7), EKS 62개 → **약 1.55배**

예상 범위 안에 들어옵니다. 실행 ②는 "EKS가 더 느린 노드에서 더 무거운 이미지로 파드를 약 1.5배 더 띄워야 했던 비교"였고, 그만큼 노드를 더 붙이는 약 6분 동안 Pending과 실패가 났다고 설명됩니다.

**조건을 다 맞췄다면 실행 ②는 (추정)**

| 항목 | 실제 (실행 ②) | 조건을 맞췄다면 |
|---|---|---|
| EKS 필요 파드 | 62개 | 약 35~45개 (온프레와 비슷) |
| EKS 추가 노드 | 5대 (3→8) | 약 2~3대, 증설 시간도 짧아짐 |
| EKS Pending 최대 | 12 | 절반 이하, 빠르게 해소 |
| EKS 실패율 | 0.32% | 온프레(0.09%)와 비슷하거나 더 낮음 — 온프레는 Pending이 끝까지 안 풀림 |

장비 · 이미지 차이가 실행 ② 결과의 대부분을 설명하고, 데몬셋은 작은 변수이며, **노드가 붙기까지 걸리는 시간은 조건을 다 맞춰도 남는 자동확장 자체의 한계**입니다. 장비를 맞춘 실행 ③에서도 초반 EKS Pending이 남았다는 점(1장)은, 이 추정만으로는 설명되지 않는 원인 6번(리소스 낭비)이 따로 있었다는 뜻입니다.

### 다시 한다면 — 실험 전에 양쪽을 대조할 것

| 확인 항목 | 이번에 놓친 것 | 확인 방법 |
|---|---|---|
| 노드 인스턴스 타입 · 세대 | t3.medium vs c8i-flex | `kubectl get nodes -L node.kubernetes.io/instance-type` |
| (T 계열이면) 크레딧 모드 | 미확인 | `aws ec2 describe-instance-credit-specifications` |
| 배포된 이미지 (태그 · 다이제스트) | `:latest` vs `:otel` | `kubectl get pods -n shoply -o jsonpath='{..imageID}'` 를 양쪽에서 비교 |
| 노드당 데몬셋 리소스 | 양쪽 구성이 다름 | `kubectl describe node`의 Allocated resources 비교 |
| 앱 파드 request · limit | gateway 메모리 128Mi vs 256Mi | 양쪽 `kubectl get deploy -o yaml`의 resources 비교 |
| 증설 속도 vs 부하 상승 속도 | 램프가 증설보다 빠름 | 시작 노드 수 · 램프 간격을 증설 시간에 맞춰 설계 |
| request vs 실제 사용량 | 노드 CPU 60~70%인데 장부상 꽉 참 | `kubectl top pods`로 실측 후 request를 맞추고, `kubectl describe node`의 requests 합계와 실제 사용률을 비교 |
| 이벤트성 초반 몰림 대비 | 노드가 Pending 이후에야 늘어남 | 이벤트 전 노드 · 파드를 미리 늘려 두거나 여유 노드 확보 |

### 배운 것
- **리소스를 아끼는 게 아니라 버리고 있었다.** request를 실제 사용량에 맞추지 못해 노드 CPU가 60~70%일 때 이미 장부상 꽉 찼고, 그 상태로 초반 몰림을 맞았습니다. 자동확장은 Pending이 나야 움직이므로, 이벤트성 트래픽에는 request를 실측으로 맞추고 미리 늘려 두는 설계가 필요합니다.
- **"자동확장이 있다"와 "부하를 버틴다"는 다르다.** 노드가 붙는 데 걸리는 시간보다 부하가 빨리 오르면, 자동확장이 있어도 그 사이엔 고정 자원과 똑같이 Pending이 쌓입니다. 실제 운영이라면 시작 노드 수를 넉넉히 두거나, 부하가 예상되는 시점 전에 미리 늘려두는 설계가 필요합니다.
- **같은 숫자가 같은 조건은 아니다.** vCPU·메모리만 맞추고 인스턴스 세대는 보지 않았고, 복기해 보니 배포된 이미지 태그까지 달랐습니다. 비교 실험에서 "같다"는 건 설계 문서가 아니라 **실제로 떠 있는 것**을 양쪽에서 대조해 확인해야 한다는 걸 배웠습니다. 장비를 맞춘 재실험(실행 ③)에서도 초반엔 EKS가 먼저 흔들렸던 것이, 맞춰야 할 것이 장비 하나가 아니었다는 증거입니다.
